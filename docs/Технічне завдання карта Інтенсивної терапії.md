# Частина 1. Загальні положення, архітектура та бізнес-процеси

# 1. Загальні положення

## 1.1 Найменування проєкту

**Модуль «Карта інтенсивної терапії» (КІТ)**

---

## 1.2 Призначення документа

Це технічне завдання визначає функціональні, нефункціональні, архітектурні та інтеграційні вимоги до розробки програмного модуля **«Карта інтенсивної терапії»**, який призначений для ведення електронної медичної документації пацієнтів відділень анестезіології та інтенсивної терапії (ВАІТ).

Документ є основою для:

- проєктування архітектури системи;
- розробки програмного забезпечення;
- створення моделі даних;
- реалізації REST API;
- інтеграції з Медичною інформаційною системою (МІС);
- автоматизованого тестування;
- приймання результатів розробки.

---

# 1.3 Мета проєкту

Метою проєкту є створення сучасного програмного модуля, який забезпечує повний цикл ведення Карти інтенсивної терапії в електронній формі, підтримує клінічні бізнес-процеси та забезпечує можливість інтеграції з існуючою Медичною інформаційною системою.

Основними завданнями модуля є:

- ведення електронної Карти інтенсивної терапії;
- погодинний моніторинг стану пацієнта;
- ведення лікарських призначень;
- контроль виконання призначень;
- автоматичний розрахунок клінічних показників;
- автоматичний розрахунок балансу рідини;
- формування медичної документації;
- забезпечення повної простежуваності всіх змін;
- підготовка до інтеграції з продуктивною МІС.

---

# 1.4 Область застосування

Модуль використовується у:

- відділеннях анестезіології;
- відділеннях інтенсивної терапії;
- палатах інтенсивної терапії;
- післяопераційних палатах інтенсивного спостереження;
- інших структурних підрозділах, де ведеться погодинний моніторинг пацієнтів.

---

# 1.5 Основні користувачі

Система підтримує наступні категорії користувачів:

| Роль | Призначення |
|------|-------------|
| Лікар | Ведення медичної карти, призначення лікування, підписання документації |
| Медична сестра | Внесення погодинного моніторингу, виконання призначень, сестринський підпис |
| Завідувач відділення | Контроль ведення документації, повторне відкриття карт |
| Адміністратор | Адміністрування системи |
| Аудитор | Перегляд журналів аудиту та історії змін |

- повноцінна інтеграція з продуктивною МІС;

- лабораторна інформаційна система (ЛІС);

- складський облік;

- електронний рецепт;
- білінг;
- електронний кабінет пацієнта;
- мобільний застосунок;
- офлайн-режим роботи.

# 4. Основні принципи побудови системи

Система повинна відповідати таким принципам:

- модульність;
- масштабованість;
- незалежність бізнес-логіки від інтеграцій;
- мінімізація дублювання даних;
- простежуваність усіх змін;
- підтримка конкурентної роботи користувачів;
- можливість безпечного розширення функціоналу;
- **односторінкова логіка роботи** — усі блоки даних однієї медичної доби відображаються на одному екрані без перемикання між сторінками, вкладками або модальними вікнами, що закривають контекст (принцип **"все перед очима"**).

---

# 5. Архітектурні принципи

При розробці системи повинні використовуватись наступні принципи:

- Clean Architecture;

- SOLID;
- Dependency Injection;
- Repository Pattern;
- CQRS (за необхідності);
- Optimistic Locking для конкурентного редагування;
- централізована обробка помилок;
- централізоване логування.

При реалізації системи необхідно дотримуватись наступних правил:

- усі зовнішні сервіси інкапсулюються окремими адаптерами;
- усі бізнес-правила реалізуються в Domain Layer.

### 11.1 Повноекранний перегляд погодинної карти

**Тригер.** Кнопка **«Розгорнути на весь екран»** (Alt+Enter) у шапці карти ІТ відкриває повноекранне модальне вікно погодинної карти (`HourlyGridDialog`). Подвійний клік по заголовку «Показник / година» також відкриває вікно (з підказкою при наведенні). На мобільних пристроях (<1200 px) кнопка завжди видима; бічна панель пацієнта приховується.

**Структура модального вікна** (`frontend/src/components/monitoring/HourlyGridDialog.tsx:85`):

- **Шапка:** ім'я пацієнта, номер доби, статус доби (кольоровий бейдж: OPEN — зелений, NURSE_SIGNED/DOCTOR_SIGNED — блакитний), кнопка критичних значень з лічильником, годинник (оновлюється що 30 с), кнопка оновлення даних і кнопка закриття (✕).
- **Панель стану:** статус збереження (автозбереження / збережено / змінено), діапазон дат доби (наприклад, «03.08.2026, 08:00–08:00»), індикатор завантаження.
- **Банер блокування:** для підписаних діб — тонкий сірий банер із замком і текстом «Доба підписана — перегляд»; усі клітинки недоступні для редагування.
- **Банер конфлікту (409):** при виявленні конкурентної модифікації — жовтий банер із кнопками «Оновити дані» (прийняти серверну версію) та «Залишити мій варіант» (перезаписати).
- **Сітка:** той самий компонент `HourlyGrid`, що й основний, у режимі `sticky` (заголовки рядків і колонок закріплені при скролі) та `bare` (без панелі інструментів).
- **Футер:** лічильник заповнення «Заповнено X/24 год», статус доби, кнопка undo «Скасувати останню зміну» (видима, але вимкнена при порожньому журналі або заблокованій добі), кнопка закриття «Назад до карти».
- **Тост відкоту виконання:** при скасуванні плану виконання з'являється тост «Виконання скасовано» з кнопкою «Скасувати» (відновлення плану).

**Клавіатурна модель (WCAG 2.4.3):**

- Початковий фокус — на кнопці закриття (✕), а не на першій редагованій клітинці, щоб уникнути випадкової зміни даних до ознайомлення зі станом пацієнта.
- `Tab` / `Shift+Tab` циклічно переміщують фокус у межах діалогу (focus trap).
- `Esc` закриває діалог; `Alt+Enter` перемикає відкриття/закриття.
- `Escape` у брудній клітинці повертає чернетку (revert); `Enter` фіксує зміну (commit).
- Фокус повертається на кнопку-тригер після закриття діалогу.

**Заходи безпеки:**

- **Undo-журнал:** до 20 останніх дій з можливістю покрокового скасування (кнопка «Скасувати останню зміну»). Скидається при зміні доби.
- **Вирішення конфліктів (HTTP 409):** банер із вибором стратегії — прийняти серверну версію або перезаписати.
- **Обізнаність про критичні значення:** кнопка-лічильник критичних показників у шапці; клік прокручує до першого критичного значення. Рейл (на мобільних) і підсвічування клітинок використовують спільний модуль `criticalRanges.ts`.
- **Відкриття/закриття без втрати даних:** `onMouseDown` preventDefault на кнопці ✕ планування запобігає гонці `onBlur` → повторне планування після скасування.
- **Друк:** правило `@media print` приховує діалоговий оверлей для коректного друку.

**Анімація.** Власні keyframes (`scale-in`, `fade-in`, `slide-in-from-left`, `content-show`) у `frontend/src/index.css`, ізольовані селектором `[data-fullscreen="true"]`. При `prefers-reduced-motion: reduce` усі анімації вимикаються.

# 14. Загальні принципи моделі даних

Модель даних модуля **«Карта інтенсивної терапії»** побудована відповідно до принципів **Domain Driven Design (DDD)** та забезпечує відокремлення клінічних даних від довідкової інформації Медичної інформаційної системи (МІС).

## Основні принципи

- Первинні дані про пацієнта, госпіталізацію, користувачів та структуру закладу не дублюються у базі даних модуля.
- Власна база даних містить лише дані, створені в процесі ведення Карти інтенсивної терапії.
- Усі записи мають унікальні ідентифікатори (UUID).
- Всі таблиці підтримують аудит та історію змін.
- Видалення медичних даних не допускається. Використовується логічне видалення або зміна статусу запису.

# 25. Загальна структура Карти інтенсивної терапії

Карта інтенсивної терапії є основним електронним медичним документом, який містить повну інформацію про перебіг лікування пацієнта протягом перебування у відділенні інтенсивної терапії.

Карта відповідає паперовій формі **003-15/о «Карта інтенсивної терапії»** (формат А4, альбомна орієнтація) та забезпечує електронне ведення всіх її розділів з можливістю друку в ідентичному вигляді.

Карта формується на рівні **епізоду лікування** та складається з окремих **медичних діб**.

Кожна медична доба містить стандартизований набір функціональних блоків.

# 37. Клінічні шкали

Система забезпечує введення та автоматичний розрахунок обов'язкового набору клінічних шкал відповідно до вимог форми № 003-15/о. Для кожної шкали визначено окремий блок, розташований безпосередньо на екрані медичної доби (або на рівні епізоду для APACHE II) відповідно до принципу «все перед очима».

## 37.1 APACHE II (один раз за епізод)

- **Рівень:** епізод лікування.
- **Хто заповнює:** лікар.
- **Коли:** протягом перших 24 годин після надходження пацієнта до ВАІТ.
- **Склад:** 12 фізіологічних параметрів (температура, середній АТ, ЧСС, ЧД, оксигенація (PaO₂/FiO₂ або A–aDO₂), pH артеріальної крові (або HCO₃⁻), Na⁺, K⁺, креатинін, гематокрит, лейкоцити, шкала коми Глазго), вік, наявність хронічних захворювань (імуносупресія, цироз, тяжка серцева/дихальна/ниркова недостатність) та гострої ниркової недостатності.
- **Розрахунок:** автоматичний. Система обчислює Acute Physiology Score (APS), додає вікові бали та бали за хронічні стани. Окремо враховується післяопераційний статус (планова/екстрена операція).
- **Особливості:**
  - Усі показники — **найгірші** значення за перші 24 години.
  - Якщо FiO₂ ≥ 50%, для оцінки оксигенації використовується альвеолярно-артеріальний градієнт (A–aDO₂).
  - За наявності гострої ниркової недостатності бали за креатинін подвоюються.
  - Після завершення 24-годинного вікна **дані не блокуються жорстко**. Виправлення можливе, але з обов'язковою фіксацією в журналі аудиту (попереднє значення, нове значення, причина змін). Система ставить позначку «ретроспективно», якщо первинне заповнення відбулося пізніше 24 годин.
- **Відображення:** результат APACHE II виводиться у блоці даних пацієнта (права колонка) та в PDF.

## 37.2 SOFA (щоденно)

- **Рівень:** медична доба.
- **Хто заповнює:** лікар (медсестра може вносити окремі лабораторні показники, але фінальне підтвердження — за лікарем).
- **Коли:** один раз на добу, за замовчуванням під час ранкового обходу (час налаштовується).
- **Розрахунок:** оцінюються 6 систем органів — дихання (PaO₂/FiO₂), коагуляція (тромбоцити, ×10⁹/л), печінка (білірубін, мкмоль/л), серцево-судинна (гіпотензія/вазопресори: допамін, добутамін, норадреналін, адреналін у мкг/кг/хв), ЦНС (шкала коми Глазго, GCS), нирки (креатинін або діурез за 24 години). Кожна система дає від 0 до 4 балів; загальний бал = сума.
- **Автопідстановка:** під час відкриття форми на нову добу система копіює компоненти попереднього дня. Лікар коригує їх на основі найгірших значень за поточну добу.
- **Відображення:** поточний бал SOFA — у блоці клінічних шкал доби, динаміка — у вигляді графіка (опціонально).

## 37.3 RASS (двічі на добу)

- **Рівень:** медична доба.
- **Хто заповнює:** лікар або медична сестра (визначається внутрішнім регламентом; система підтримує обидві ролі).
- **Коли:** два фіксовані часові слоти (за замовчуванням 08:00 та 20:00, адміністратор може змінити).
- **Значення:** вибір із шкали від -5 (не пробуджується) до +4 (агресивний). Результат фіксується з часовою міткою.
- **Відображення:** два слоти на добу з випадаючим списком, поруч із CAM-ICU.

## 37.4 CAM-ICU (двічі на добу)

- **Рівень:** медична доба.
- **Хто заповнює:** лікар або медична сестра (аналогічно RASS).
- **Коли:** синхронно з RASS у ті ж самі часові слоти.
- **Оцінка:** чотири ознаки (гостра зміна/коливання психічного статусу, неуважність, дезорганізоване мислення, змінений рівень свідомості). Система автоматично визначає бінарний результат: «делірій є», якщо Ознака 1 + Ознака 2 + (Ознака 3 або Ознака 4) позитивні; інакше «делірію немає».
- **Відображення:** чек-лист ознак, підсумковий бінарний результат.

## 37.5 Шкала Браден (двічі на добу)

- **Рівень:** медична доба.
- **Хто заповнює:** медична сестра.
- **Коли:** ті самі часові слоти, що й RASS/CAM-ICU.
- **Оцінка:** 6 підшкал (чутливість, вологість, активність, рухливість, харчування, тертя/зсув). Бали підсумовуються. Загальний бал зберігається.

Усі шкали зберігаються з автором, часом введення та (за потреби) позначкою про підтвердження лікарем. Після підписання доби дані стають незмінними.

# 40. PDF документа

PDF формується після підписання медичної доби (або за запитом) у форматі **A4, альбомна орієнтація**.

## Формат та типографіка

- **Формат сторінки:** A4 landscape (297 × 210 мм)
- **Гарнітура:** Times New Roman (основна), DejaVu Sans (fallback для кирилиці)
- **Розмір шрифту:** 6–8 pt для табличних даних, 10–12 pt для заголовків
- **Поля:** 10–15 мм з усіх боків
- **Табличний макет** — відображення даних у вигляді сітки, ідентичної формі 003-15/о

## Структура PDF-документа

Документ містить наступні секції:

| Секція | Вміст |
|--------|-------|
| Заголовок | Назва закладу, назва документа, номер епізоду, дата доби |
| Дані пацієнта | ПІБ, дата народження, стать, зріст, вага, група крові/резус |
| Дані госпіталізації | Діагноз, дата надходження, відділення |
| Погодинний моніторинг | Таблиця 24 год × 8 показників (свідомість, t°, ЧСС, ЧД, АТсист/АТдіаст, SpO₂, глюкоза) з комірками для кожної години |
| Шкали оцінки | APACHE II, SOFA, RASS, CAM-ICU, Брейден |
| Терапія | 9-рядкова таблиця інфузійної терапії з годинами введення |
| Втрати | 4-рядкова таблиця втрат рідини |
| Баланс рідини | Загальне надходження / загальні втрати / баланс / кумулятивний баланс |
| Лікарські призначення | Перелік активних і виконаних призначень |
| Лабораторні показники | Загальний аналіз крові, біохімія, гази крові, коагулограма |
| Медичні нотатки | Лікарські та сестринські записи |
| Підписи | Електронні підписи медсестри та лікаря з датою/часом |
| Службова інформація | Версія документа, дата генерації, ПІБ лікаря/сестри |

## Поведінка

- Після генерації PDF не може змінюватися (імутабельний документ).
- У разі повторного відкриття доби формується нова версія PDF (інкремент `fileVersion`).
- Після генерації PDF передається до МІС (`transferStatus: PENDING → SENT/FAILED`).

# 42. Загальні вимоги до всіх блоків

Кожен блок карти повинен:

- підтримувати автоматичне збереження;
- проходити валідацію введених даних;
- підтримувати історію змін;
- бути доступним відповідно до ролі користувача;
- блокувати редагування після підписання;
- підтримувати механізм конкурентного редагування (Optimistic Locking);
- бути включеним до сформованого PDF-документа.

# 43. Правила відображення

## Загальні правила

- Дані групуються за медичними добами.
- Активна доба відображається першою.
- Підписані доби доступні лише для перегляду.
- Повторно відкриті доби мають відповідну позначку.
- Критичні значення показників повинні бути візуально виділені.
- Всі автоматично розраховані поля повинні бути позначені як обчислювані та не допускають ручного редагування.

## Компоновка сторінки (Frontend)

- **Односторінкова логіка:** всі блоки однієї медичної доби відображаються на одному екрані без перемикання вкладок/сторінок/модальних вікон («все перед очима»).
- **Двоколонковий макет:** основна таблична частина (погодинний моніторинг, шкали) займає ліву колонку; бокова панель (дані пацієнта, антропометрія, група крові, APACHE II, SOFA, баланс рідини, підписи) — праву колонку фіксованої ширини ~300px.
- **Без акардеонів:** всі секції завжди розгорнуті, жодних вкладок або згортальних блоків.
- **Автоматичне збереження:** зміни зберігаються без ручного натискання кнопки збереження (див. §60).

## Компоновка PDF

- PDF генерується у форматі A4 landscape з табличним макетом, ідентичним паперовій формі 003-15/о (див. §40).
- Секції розташовуються зверху вниз: заголовок, дані пацієнта, погодинна таблиця, терапія, втрати, баланс, призначення, лабораторія, нотатки, підписи.
- Бокова панель (дані пацієнта, антропометрія) інтегрується у верхню частину сторінки PDF як окремі рядки таблиці.

# Частина 4. Бізнес-правила та алгоритми

# 44. Загальні бізнес-правила

Модуль **«Карта інтенсивної терапії»** реалізує бізнес-процеси ведення медичної документації у відділенні інтенсивної терапії відповідно до клінічних вимог та внутрішніх регламентів закладу.

Усі бізнес-правила виконуються виключно на рівні **Domain Layer** та не залежать від інтерфейсу користувача або способу інтеграції з МІС.

---

# 45. Життєвий цикл Карти інтенсивної терапії

Карта проходить послідовні стани:

```text
Створення епізоду
        │
        ▼
Активна карта
        │
        ▼
Відкрита медична доба
        │
        ▼
Заповнення даних
        │
        ▼
Підпис медичної сестри
        │
        ▼
Підпис лікаря
        │
        ▼
Закрита медична доба
        │
        ▼
Формування PDF
        │
        ▼
Архівування
```

Після підписання лікарем медична доба переходить у режим **лише читання**.

---

# 46. Бізнес-правила створення епізоду

## Основні правила

- Епізод створюється лише для пацієнта, який існує в МІС.
- Один пацієнт може мати декілька історичних епізодів.
- Одночасно може існувати лише один активний епізод лікування у ВАІТ.
- Дані пацієнта імпортуються з МІС та доступні лише для читання.
- Створення епізоду журналюється.

---

# 47. Бізнес-правила медичної доби

## Загальні правила

- Медична доба є основною одиницею ведення документації.
- Кожна медична доба належить одному епізоду.
- Одночасно може бути відкритою лише одна медична доба.
- Наступна доба створюється лише після завершення попередньої.
- Повторне відкриття закритої доби дозволяється лише користувачам із відповідними правами.

---

# 48. Бізнес-правила погодинного моніторингу

Для кожної медичної доби формується набір погодинних записів.

## Правила

- Один погодинний запис відповідає одній часовій позначці.
- Для кожної години допускається лише один запис.
- Запис може редагуватися до підписання медичної доби.
- Після підписання редагування заборонене.
- Кожна зміна автоматично журналюється.

---

# 49. Валідація клінічних показників

Система повинна перевіряти:

- обов'язковість заповнення полів;
- тип даних;
- допустимі діапазони значень;
- логічну узгодженість показників.

При введенні значень поза допустимими межами система:

- попереджає користувача;
- дозволяє збереження лише після підтвердження (за налаштованими правилами);
- фіксує подію в журналі аудиту.

# 50. Бізнес-правила лікарських призначень

Лікарське призначення може створювати лише користувач із роллю **Лікар** або **Завідувач відділення**.

Призначення повинно містити:

- препарат або втручання;
- дозування;
- спосіб введення;
- кратність;
- час початку;
- час завершення (за потреби).

Статуси призначення:

- Draft
- Active
- Completed
- Cancelled

Після виконання призначення його редагування забороняється.

# 51. Бізнес-правила виконання призначень

Виконання призначення здійснює медична сестра.

Для кожного виконання фіксуються:

- дата та час;
- виконавець;
- фактична доза або обсяг;
- статус виконання;
- коментар (за потреби).

Дозволяються стани:

- Planned
- InProgress
- PartiallyCompleted
- Completed
- Cancelled

Усі зміни автоматично журналюються.

# 52. Алгоритм розрахунку балансу рідини

Баланс рідини розраховується автоматично після кожної зміни даних.

## Надходження

Враховуються:

- інфузійні розчини;
- препарати;
- кров;
- плазма;
- ентеральне харчування;
- парентеральне харчування;
- пероральне введення;
- інші джерела.

## Втрати

Враховуються:

- діурез;
- дренажі;
- блювання;
- кал;
- крововтрата;
- аспірація;
- інші втрати.

## Результати

Автоматично обчислюються:

```text
Баланс за годину

=

Надходження

-

Втрати
```

```text
Добовий баланс

=

Σ погодинних балансів
```

```text
Кумулятивний баланс

=

Попередній кумулятивний баланс

+

Добовий баланс
```

Перерахунок виконується автоматично після будь-якої зміни вхідних даних.

# 53. Алгоритми клінічних шкал

Усі обчислення виконуються на рівні Domain Layer, вони детерміновані та покриті Unit-тестами.

## 53.1 APACHE II

```text
APS = Σ бали за 12 фізіологічних параметрів (кожен 0–4)
Вікові бали: <=44 – 0; 45-54 – 2; 55-64 – 3; 65-74 – 5; >=75 – 6
Хронічні бали: якщо є тяжка органна недостатність або імунодефіцит:
  - нехірургічний / плановий хірургічний пацієнт – 2 бали;
  - екстрений хірургічний пацієнт – 5 балів.
APACHE II = APS + вікові бали + хронічні бали

Розрахунок балів за оксигенацію залежить від FiO₂:
  Якщо FiO₂ < 50% — використовується PaO₂.
  Якщо FiO₂ ≥ 50% — обчислюється A-aDO₂ = (713 × FiO₂) – (PaCO₂ / 0.8) – PaO₂.

Система повинна підтримувати сценарій відсутності артеріальних газів крові (тоді використовується сироватковий HCO₃⁻).
```

## 53.2 SOFA

```text
Дихання: PaO₂/FiO₂, мм рт. ст.
  >400 – 0; 300–400 – 1; 200–300 – 2; 100–200 + ШВЛ – 3; <100 + ШВЛ – 4
Коагуляція: тромбоцити, ×10⁹/л (×10³/мм³)
  >150 – 0; 100–150 – 1; 50–100 – 2; 20–50 – 3; <20 – 4
Печінка: білірубін, мг/дл (мкмоль/л)
  <1.2 (<20) – 0; 1.2–1.9 (20–32) – 1; 2.0–5.9 (33–101) – 2;
  6.0–11.9 (102–204) – 3; >12.0 (>204) – 4
Серцево-судинна: гіпотензія/вазопресори (дози — мкг/кг/хв)
  MAP ≥70 – 0; MAP <70 – 1;
  допамін ≤5 або добутамін (будь-яка доза) – 2;
  допамін >5 або норадреналін ≤0.1 або адреналін ≤0.1 – 3;
  допамін >15 або норадреналін >0.1 або адреналін >0.1 – 4
ЦНС: шкала коми Глазго (GCS)
  15 – 0; 13–14 – 1; 10–12 – 2; 6–9 – 3; <6 – 4
Нирки: креатинін, мг/дл (мкмоль/л) або діурез за 24 години
  <1.2 (<110) – 0; 1.2–1.9 (110–170) – 1; 2.0–3.4 (171–299) – 2;
  3.5–4.9 (300–440) або діурез <500 мл/д – 3;
  >5.0 (>440) або діурез <200 мл/д – 4
```

## 53.3 RASS

Шкала від -5 до +4 з описом рівнів. Система зберігає обране числове значення.

## 53.4 CAM-ICU

```text
Ознака 1: гостра зміна або коливання психічного статусу (так/ні)
Ознака 2: неуважність (так/ні)
Ознака 3: дезорганізоване мислення (так/ні)
Ознака 4: змінений рівень свідомості (RASS від -3 до +4?) (так/ні)
Делірій є, якщо Ознака 1 + Ознака 2 + (Ознака 3 або Ознака 4) позитивні.
```

## 53.5 Браден

```text
Сума балів за 6 підшкалами (кожна 1–4, крім тертя/зсув 1–3).
Максимум 23 бали.
Ризик пролежнів: 15–18 – легкий, 13–14 – помірний, 10–12 – високий, ≤9 – дуже високий.
```

# 55. Бізнес-правила електронного підписання

Підписання здійснюється у визначеній послідовності:

1. Медична сестра.

- документ блокується;

# 56. Повторне відкриття медичної доби

Повторне відкриття дозволяється лише користувачам із відповідними правами.

Обов'язкові умови:

- зазначення причини;
- журналювання події;
- скасування попередніх підписів;
- повторне підписання після завершення змін.

# 57. Генерація PDF

PDF формується після підписання медичної доби (можлива також генерація за запитом через API).

## Формат

- **A4 landscape** (297 × 210 мм)
- Гарнітура: Times New Roman, DejaVu Sans (fallback)
- Табличний макет, ідентичний паперовій формі 003-15/о

## Секції PDF-документа (у порядку відображення)

1. **Заголовок** — назва закладу, назва документа, номер епізоду, ПІБ лікаря/сестри
2. **Дані пацієнта + антропометрія** — ПІБ, вік, стать, зріст, вага, група крові/резус, APACHE II, SOFA
3. **Погодинна таблиця** — 24 колонки (години) × рядки показників (свідомість, t°, ЧСС, ЧД, АТсист, АТдіаст, SpO₂, глюкоза та ін.)
4. **Терапія** — 9-рядкова таблиця інфузійної терапії
5. **Втрати** — 4-рядкова таблиця втрат рідини
6. **Баланс рідини** — надходження / втрати / баланс / кумулятивний баланс
7. **Лікарські призначення**
8. **Лабораторні показники**
9. **Медичні нотатки**
10. **Підписи** — медсестра + лікар з датою/часом

## Поведінка

- Після генерації PDF не може змінюватися (імутабельний документ).
- У разі повторного відкриття доби формується нова версія PDF (інкремент `fileVersion`).
- Після генерації PDF передається до МІС з відстеженням статусу (`transferStatus`).
- Всі операції генерації PDF журналюються в аудиті.

# 58. Правила аудиту

Аудиту підлягають:

- створення;
- зміна;
- підписання;
- повторне відкриття;
- видалення службових записів;
- інтеграційні виклики;
- авторизація;
- системні помилки.

Для кожної події зберігаються:

- дата;
- час;
- користувач;
- роль;
- дія;
- об'єкт;
- попереднє значення;
- нове значення;
- Correlation ID.

# 59. Конкурентне редагування

Для всіх основних сутностей використовується **Optimistic Locking**.

Кожний запис містить поле:

```text
Version
```

При одночасному редагуванні:

1. Перший користувач успішно зберігає зміни.
2. Другий отримує відповідь:

```http
409 Conflict
```

Користувач повинен оновити дані та повторити зміни.

---

# 60. Автоматичне збереження

Система підтримує автоматичне збереження без необхідності ручного натискання кнопки збереження.

## Правила

- збереження після завершення редагування поля (подія blur/debounce);
- періодичне збереження активної форми;
- повідомлення користувача про помилки;
- відновлення незбережених даних після короткочасного збою (за наявності локального кешу).

## Реалізація (Frontend)

- **Хук `useAutoSave`** — універсальний механізм автозбереження для всіх панелей (погодинний моніторинг, лікарські призначення, медичні нотатки, клінічні шкали).
- **Тригер:** втрата фокусу полем (`onBlur`) або зміна значення після затримки (debounce ~1000 мс).
- **Індикатор статусу:** візуальне відображення стану збереження (зберігається / збережено / помилка) безпосередньо біля редагованого поля.
- **Оптимістичне оновлення:** дані оновлюються в UI негайно, запит до сервера виконується асинхронно.
- **Ізоляція панелей:** кожна панель має власний `useAutoSave` з незалежним статусом, помилки однієї панелі не впливають на інші.
- **Механізм:** `PATCH`-запит до відповідного API-ендпоінта з `version` для optimistic locking (HTTP 409 при конфлікті).

# 65. Загальні принципи інтеграції

Модуль **«Карта інтенсивної терапії»** є окремим сервісом, який інтегрується з Медичною інформаційною системою (МІС) через стандартизований Integration Layer.

Перехід до продуктивної МІС повинен виконуватися шляхом заміни Mock Adapter без внесення змін до бізнес-логіки.

# 67. Принципи взаємодії — ПОЛІТИКА READ-ONLY ДОСТУПУ

**Модуль КІТ є виключно READ-ONLY клієнтом МІС.**

## Категорична заборона

**ЗАБОРОНЕНО** змінювати будь-які дані на стороні МІС, включаючи:

- створення, редагування, видалення пацієнтів (`spzIBPatientCreate`, `spzIBPatientSave`);
- створення, редагування, скасування візитів/записів (`spzIBScheduleCreate`, `spzIBScheduleCancel`);
- створення, редагування агентів (`spzIBAgentSave`);
- створення, редагування установ (`spzIBInstitutionSave`);
- створення, редагування послуг (`spzIBServiceSave`);
- створення, редагування вартості послуг (`spzIBServicePriceSave`);
- будь-які інші методи з префіксами `Save`, `Create`, `Update`, `Delete`, `Cancel` у специфікації API МІС.

## Єдиний дозволений виняток

**Виключно** дозволяється надсилання сформованого PDF-документа до картки пацієнта в МІС через метод `sendPdf()`. Цей метод передає **immutable** PDF-документ і не змінює жодних існуючих записів у МІС.

## Дозволені read-only операції

У межах MVP модуль лише **отримує** дані з МІС:

- отримує інформацію про пацієнта (`spzIBPatientSearch`);
- отримує інформацію про госпіталізацію (`spzIBPatientScheduleList`);
- отримує інформацію про користувачів (`spzIBUserDetails`);
- отримує інформацію про відділення (`spzIBCompanyDetails`);
- отримує локальні довідники МІС (`spzIB*Dictionary`).

Усі медичні дані (епізоди, медичні доби, погодинний моніторинг, призначення, виконання, баланс рідини, клінічні шкали, нотатки, підписи) створюються та зберігаються виключно у власній базі даних модуля та **ніколи не передаються до МІС**.

Порушення цієї політики призведе до пошкодження цілісності даних МІС та є категорично неприпустимим.

# 73. Вимоги до Integration Layer

Integration Layer повинен:

- інкапсулювати всі виклики до МІС;
- приховувати від бізнес-логіки деталі API МІС;
- виконувати мапування моделей МІС у внутрішні DTO;
- централізовано обробляти помилки інтеграції;
- підтримувати заміну Mock Adapter на Production Adapter без зміни інших компонентів системи.

---

# 74. Вимоги до Mock Adapter

Mock Adapter повинен:

- реалізовувати ті самі REST-контракти, що й API МІС;
- повертати тестові дані, максимально наближені до продуктивних;
- підтримувати сценарії успішної відповіді та типових помилок (404, 409, 500, timeout);
- використовуватися під час локальної розробки, автоматизованих тестів та виконання GitHub Actions.

---

# 75. Обмеження MVP

У поточній версії проєкту:

- **категорично заборонено запис даних до МІС** — модуль є виключно read-only клієнтом (єдиний виняток — `sendPdf()` для передачі сформованого PDF до картки пацієнта);
- **не використовується продуктивне API МІС** — усі інтеграційні сценарії працюють виключно через Mock Integration Layer;
- **не реалізується синхронізація медичної документації з МІС** — усі клінічні дані створюються та зберігаються у власній БД модуля;
- будь-які методи запису API МІС (`*Save`, `*Create`, `*Update`, `*Delete`, `*Cancel`) не використовуються та не повинні бути реалізовані в Integration Layer;
- перехід до продуктивної інтеграції є окремим етапом розвитку системи та не входить до складу MVP.

- журналювання всіх критичних подій.

Після підписання медична документація переходить у режим **тільки читання**.

---

# 80. Журнал аудиту

Журнал аудиту є невід'ємною частиною системи та забезпечує простежуваність усіх критичних дій.

## Обов'язково журналюються

- авторизація користувача;
- завершення сесії;
- відкриття епізоду;
- створення медичної доби;
- редагування будь-якого медичного запису;
- створення та зміна лікарських призначень;
- виконання призначень;
- автоматичні перерахунки;
- підписання документа;
- повторне відкриття документа;
- генерація PDF;
- інтеграційні виклики;
- системні помилки.

---

## Для кожного запису аудиту зберігаються

- дата;
- час;
- користувач;
- роль;
- IP-адреса (за наявності);
- Correlation ID;
- назва операції;
- тип сутності;
- ідентифікатор сутності;
- попереднє значення (за потреби);
- нове значення (за потреби).

Журнал аудиту не може бути змінений або видалений користувачами.

---

# 81. Логування

Система повинна вести централізоване структуроване логування.

Логуються:

- запуск сервісів;
- завершення роботи;
- REST-запити;
- виклики Integration Layer;
- SQL-помилки;
- бізнес-помилки;
- виняткові ситуації;
- час виконання операцій.

Логи не повинні містити конфіденційних медичних даних або персональної інформації, якщо це не передбачено політикою безпеки.

---

# 82. Обробка помилок

Усі помилки повертаються у стандартизованому форматі.

```json
{
  "code": "DOCUMENT_LOCKED",
  "message": "Clinical day is signed and cannot be modified.",
  "correlationId": "..."
}
```

Система не повинна повертати користувачу стек викликів або службову інформацію.

---

# 83. Конкурентне редагування

Для всіх основних сутностей використовується механізм **Optimistic Locking**.

При конфлікті версій API повертає:

```http
409 Conflict
```

Зміни не повинні втрачатися навіть при одночасній роботі декількох користувачів.

# 84. Резервне копіювання та відновлення

Система повинна підтримувати:

- резервне копіювання бази даних;
- відновлення після збою;
- цілісність транзакцій;
- відновлення після перезапуску сервісів.

# 85. AI-Driven Development

Розробка програмного забезпечення виконується із застосуванням **AI-агента як основного виконавця**.

Вимоги до процесу:

- вихідний код зберігається у Git-репозиторії;
- будь-які зміни повинні бути відтворюваними;
- кожна реалізована функція супроводжується автоматизованими тестами;
- зміни не можуть бути інтегровані без успішного проходження CI.

# 86. Continuous Integration

Для кожного **Push** та **Pull Request** автоматично запускається **GitHub Actions**.

Pipeline повинен виконувати:

1. Збірку проєкту.
2. Перевірку форматування коду.
3. Статичний аналіз.
4. Запуск Unit Tests.
5. Запуск Integration Tests.
6. Запуск Function (End-to-End) Tests.
7. Формування звіту про покриття тестами.
8. Публікацію артефактів збірки.

У разі помилки будь-якого етапу зміни не можуть бути інтегровані до основної гілки.

Розробка MVP вважається завершеною після виконання всіх критеріїв приймання.

## 90.1 Функціональні критерії

- погодинний моніторинг;
- лікарські призначення;
- виконання призначень;
- автоматичний розрахунок балансу рідини;
- підтримка клінічних шкал;
- медичні нотатки;
- електронне підписання (Mock);
- генерація PDF;
- журнал аудиту;
- REST API модуля;
- Mock Integration Layer відповідно до контрактів API МІС.

## 90.2 Нефункціональні критерії

| Показник | Цільове значення |
|-----------|-----------------:|
| Відкриття карти | ≤ 2 с |
| Збереження запису | ≤ 500 мс |
| Формування PDF | ≤ 10 с |
| Відповідь REST API (95-й перцентиль) | ≤ 500 мс |
| Одночасні користувачі | ≥ 50 |

---

## 90.3 Критерії якості

- критична бізнес-логіка покрита Unit Tests не менше ніж на **80%**;
- усі інтеграційні сценарії покриті Integration Tests;
- основні бізнес-процеси покриті Playwright Function Tests;
- відсутні критичні (Critical) та високопріоритетні (High) дефекти;
- усі зміни проходять повний CI Pipeline.

---

## 90.4 Критерії інтеграції

- Mock Adapter реалізує необхідні контракти API МІС;
- бізнес-логіка не містить прямих викликів API МІС;
- заміна Mock Adapter на Production Adapter не потребує змін Domain Layer або REST API.

---

## 90.5 Критерії приймання Замовником

Модуль вважається готовим до передачі Замовнику, якщо:

1. Виконано всі вимоги цього технічного завдання.
2. Успішно пройдено Unit, Integration та Function Testing.
3. GitHub Actions успішно завершує повний CI Pipeline.
4. Продемонстровано повний сценарій роботи системи на Mock-даних: від відкриття епізоду до формування та підписання PDF.
5. Замовнику передано вихідний код, документацію, інструкцію з розгортання та результати автоматизованого тестування.
6. Замовник підтвердив відповідність реалізованого функціоналу технічному завданню актом приймання-передачі або іншим погодженим документом.
