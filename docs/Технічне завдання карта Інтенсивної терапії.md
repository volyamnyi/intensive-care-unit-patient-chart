# Частина 1. Загальні положення, архітектура та бізнес-процеси

---

# 1. Загальні положення

## 1.1 Найменування проєкту

**Модуль «Карта інтенсивної терапії» (КІТ)**

---

## 1.2 Призначення документа

Це технічне завдання визначає функціональні, нефункціональні, архітектурні та інтеграційні вимоги до розробки програмного модуля **«Карта інтенсивної терапії»**, який призначений для ведення електронної медичної документації пацієнтів відділень анестезіології та інтенсивної терапії (ВАІТ).

Документ є основою для:

- проєктування архітектури системи;
- розробки програмного забезпечення;
- створення моделі даних;
- реалізації REST API;
- інтеграції з Медичною інформаційною системою (МІС);
- автоматизованого тестування;
- приймання результатів розробки.

---

# 1.3 Мета проєкту

Метою проєкту є створення сучасного програмного модуля, який забезпечує повний цикл ведення Карти інтенсивної терапії в електронній формі, підтримує клінічні бізнес-процеси та забезпечує можливість інтеграції з існуючою Медичною інформаційною системою.

Основними завданнями модуля є:

- ведення електронної Карти інтенсивної терапії;
- погодинний моніторинг стану пацієнта;
- ведення лікарських призначень;
- контроль виконання призначень;
- автоматичний розрахунок клінічних показників;
- автоматичний розрахунок балансу рідини;
- формування медичної документації;
- забезпечення повної простежуваності всіх змін;
- підготовка до інтеграції з продуктивною МІС.

---

# 1.4 Область застосування

Модуль використовується у:

- відділеннях анестезіології;
- відділеннях інтенсивної терапії;
- палатах інтенсивної терапії;
- післяопераційних палатах інтенсивного спостереження;
- інших структурних підрозділах, де ведеться погодинний моніторинг пацієнтів.

---

# 1.5 Основні користувачі

Система підтримує наступні категорії користувачів:

| Роль | Призначення |
|------|-------------|
| Лікар | Ведення медичної карти, призначення лікування, підписання документації |
| Медична сестра | Внесення погодинного моніторингу, виконання призначень, сестринський підпис |
| Завідувач відділення | Контроль ведення документації, повторне відкриття карт |
| Адміністратор | Адміністрування системи |
| Аудитор | Перегляд журналів аудиту та історії змін |

# 2. Нормативна база

При розробці модуля необхідно керуватися:

- чинним законодавством України у сфері охорони здоров'я;
- нормативно-правовими актами щодо ведення медичної документації;
- вимогами щодо захисту персональних даних;
- внутрішніми регламентами Замовника;
- специфікацією API Медичної інформаційної системи;
- вимогами цього технічного завдання.

---

# 3. Межі проєкту

До складу MVP входить:

- ведення електронної Карти інтенсивної терапії;
- управління епізодами лікування;
- погодинний моніторинг;
- ведення лікарських призначень;
- виконання призначень;
- розрахунок клінічних показників;
- автоматичний розрахунок балансу рідини;
- ведення клінічних шкал;
- формування PDF документа;
- журнал аудиту;
- REST API модуля;
- Integration Layer;
- Mock Adapter для інтеграції з МІС.

---

## Не входить до MVP

У межах поточного проєкту не реалізуються:

- повноцінна інтеграція з продуктивною МІС;
- інтеграція з eHealth;
- лабораторна інформаційна система (ЛІС);
- PACS/RIS;
- аптечний модуль;
- складський облік;
- фінансові модулі;
- електронний рецепт;
- білінг;
- електронний кабінет пацієнта;
- мобільний застосунок;
- офлайн-режим роботи.

# 4. Основні принципи побудови системи

Система повинна відповідати таким принципам:

- модульність;
- масштабованість;
- незалежність бізнес-логіки від інтеграцій;
- мінімізація дублювання даних;
- простежуваність усіх змін;
- підтримка конкурентної роботи користувачів;
- можливість безпечного розширення функціоналу.

---

# 5. Архітектурні принципи

При розробці системи повинні використовуватись наступні принципи:

- Clean Architecture;
- Domain Driven Design (DDD) для предметної області;
- SOLID;
- Dependency Injection;
- Repository Pattern;
- CQRS (за необхідності);
- Optimistic Locking для конкурентного редагування;
- централізована обробка помилок;
- централізоване логування.

# 8. Архітектурні обмеження

При реалізації системи необхідно дотримуватись наступних правил:

- бізнес-логіка не повинна містити SQL-запитів;
- бізнес-логіка не повинна напряму викликати API МІС;
- усі інтеграції виконуються виключно через Integration Layer;
- доступ до бази даних здійснюється через Repository;
- усі зовнішні сервіси інкапсулюються окремими адаптерами;
- усі бізнес-правила реалізуються в Domain Layer.

# 14. Загальні принципи моделі даних

Модель даних модуля **«Карта інтенсивної терапії»** побудована відповідно до принципів **Domain Driven Design (DDD)** та забезпечує відокремлення клінічних даних від довідкової інформації Медичної інформаційної системи (МІС).

## Основні принципи

- Первинні дані про пацієнта, госпіталізацію, користувачів та структуру закладу не дублюються у базі даних модуля.
- Власна база даних містить лише дані, створені в процесі ведення Карти інтенсивної терапії.
- Усі записи мають унікальні ідентифікатори (UUID).
- Всі таблиці підтримують аудит та історію змін.
- Видалення медичних даних не допускається. Використовується логічне видалення або зміна статусу запису.

# 21. Правила версіонування

Усі основні сутності повинні містити поле:

```text
Version
```

Поле використовується механізмом **Optimistic Locking** для запобігання втраті даних при одночасному редагуванні.

При конфлікті версій API повертає:

```http
409 Conflict
```

# 22. Загальні службові поля

Усі основні таблиці повинні містити стандартний набір службових полів.

| Поле | Призначення |
|------|-------------|
| Id | UUID |
| CreatedAt | Дата створення |
| CreatedBy | Автор створення |

# 23. Вимоги до бази даних

Для зберігання даних використовується **PostgreSQL**.

Основні вимоги:

- підтримка ACID-транзакцій;
- використання UUID як первинних ключів;
- індексація зовнішніх ключів;
- індексація полів пошуку (`EpisodeId`, `ClinicalDayId`, `RecordTime`, `Status`);
- підтримка Optimistic Locking;
- резервне копіювання;
- журналювання транзакцій;
- можливість міграцій структури бази даних без втрати даних.

- відтворюваність середовищ;
- автоматичне розгортання;
- можливість відкату (rollback) для змін, де це технічно можливо;

# 44. Загальні бізнес-правила

Модуль **«Карта інтенсивної терапії»** реалізує бізнес-процеси ведення медичної документації у відділенні інтенсивної терапії відповідно до клінічних вимог та внутрішніх регламентів закладу.

Усі бізнес-правила виконуються виключно на рівні **Domain Layer** та не залежать від інтерфейсу користувача або способу інтеграції з МІС.

# 45. Життєвий цикл Карти інтенсивної терапії

Карта проходить послідовні стани:

```text
        │
        ▼

        │

        │
        ▼

```

Після підписання лікарем медична доба переходить у режим **лише читання**.

# 46. Бізнес-правила створення епізоду

## Основні правила

- Епізод створюється лише для пацієнта, який існує в МІС.
- Один пацієнт може мати декілька історичних епізодів.
- Одночасно може існувати лише один активний епізод лікування у ВАІТ.
- Дані пацієнта імпортуються з МІС та доступні лише для читання.
- Створення епізоду журналюється.

---

# 47. Бізнес-правила медичної доби

## Загальні правила

- Медична доба є основною одиницею ведення документації.
- Кожна медична доба належить одному епізоду.
- Одночасно може бути відкритою лише одна медична доба.
- Наступна доба створюється лише після завершення попередньої.
- Повторне відкриття закритої доби дозволяється лише користувачам із відповідними правами.

---

# 48. Бізнес-правила погодинного моніторингу

Для кожної медичної доби формується набір погодинних записів.

## Правила

- Один погодинний запис відповідає одній часовій позначці.
- Для кожної години допускається лише один запис.
- Запис може редагуватися до підписання медичної доби.
- Після підписання редагування заборонене.
- Кожна зміна автоматично журналюється.

---

# 49. Валідація клінічних показників

Система повинна перевіряти:

- обов'язковість заповнення полів;
- тип даних;
- допустимі діапазони значень;
- логічну узгодженість показників.

При введенні значень поза допустимими межами система:

- попереджає користувача;
- дозволяє збереження лише після підтвердження (за налаштованими правилами);
- фіксує подію в журналі аудиту.

# 53. Алгоритми клінічних шкал

Система підтримує два режими роботи:

## Автоматичний

## Ручний

Для шкал без алгоритму користувач вводить підсумковий бал вручну.

Для кожного результату зберігаються:

- дата та час;

- отриманий результат.

PDF формується після завершення медичної доби.

Документ містить:

- усі медичні записи;
- результати автоматичних розрахунків;
- клінічні шкали;
- підписи;
- службову інформацію.

Після генерації PDF не може змінюватися.

У разі повторного відкриття доби формується нова версія PDF.

Аудиту підлягають:

- створення;
- зміна;
- підписання;
- повторне відкриття;
- видалення службових записів;
- інтеграційні виклики;
- авторизація;
- системні помилки.

- роль;

- попереднє значення;
- нове значення;

# 59. Конкурентне редагування

Для всіх основних сутностей використовується **Optimistic Locking**.

Кожний запис містить поле:

```text
Version
```

При одночасному редагуванні:

1. Перший користувач успішно зберігає зміни.
2. Другий отримує відповідь:

```http
409 Conflict
```

Користувач повинен оновити дані та повторити зміни.

---

# 60. Автоматичне збереження

Система підтримує автоматичне збереження.

Правила:

- збереження після завершення редагування поля;
- періодичне збереження активної форми;
- повідомлення користувача про помилки;
- відновлення незбережених даних після короткочасного збою (за наявності локального кешу).

---

# 61. Бізнес-правила інтеграції з МІС

Усі виклики виконуються виключно через **Integration Layer**.

На етапі MVP використовується **Mock Adapter**, який повторює контракти API МІС.

Бізнес-логіка не повинна залежати від конкретної реалізації інтеграції.

---

# 62. Правила доступу

Доступ до функціоналу визначається роллю користувача.

Основні правила:

- лише лікар може створювати або змінювати призначення;
- лише медична сестра може підтверджувати виконання призначень;
- повторне відкриття доби доступне лише уповноваженим ролям;
- підписання документа виконується відповідно до ролі;
- користувач може переглядати лише дані, до яких має права доступу.

# 63. Обробка помилок

Усі бізнес-помилки повинні повертатися у стандартизованому форматі.

Приклади:

| Код | Опис |

# 64. Загальні алгоритмічні вимоги

Усі алгоритми системи повинні:

# 65. Загальні принципи інтеграції

Модуль **«Карта інтенсивної терапії»** є окремим сервісом, який інтегрується з Медичною інформаційною системою (МІС) через стандартизований Integration Layer.

На етапі **MVP** взаємодія з МІС здійснюється **виключно через Mock Integration Layer**, який реалізує контракти продуктивного API МІС.

Бізнес-логіка, REST API та модель даних не повинні залежати від конкретної реалізації інтеграції.

Перехід до продуктивної МІС повинен виконуватися шляхом заміни Mock Adapter без внесення змін до бізнес-логіки.

# 72. HTTP Status Codes

| Код | Використання |
|------|--------------|
| 200 | Успішний запит |

| 204 | Успішне виконання без тіла відповіді |

| 401 | Неавторизований користувач |
| 403 | Недостатньо прав |
| 404 | Об'єкт не знайдено |

| 500 | Внутрішня помилка сервера |

# 73. Вимоги до Integration Layer

Integration Layer повинен:

- інкапсулювати всі виклики до МІС;
- приховувати від бізнес-логіки деталі API МІС;
- виконувати мапування моделей МІС у внутрішні DTO;
- централізовано обробляти помилки інтеграції;
- підтримувати заміну Mock Adapter на Production Adapter без зміни інших компонентів системи.

---

# 74. Вимоги до Mock Adapter

Mock Adapter повинен:

- реалізовувати ті самі REST-контракти, що й API МІС;
- повертати тестові дані, максимально наближені до продуктивних;
- підтримувати сценарії успішної відповіді та типових помилок (404, 409, 500, timeout);
- використовуватися під час локальної розробки, автоматизованих тестів та виконання GitHub Actions.

---

# 75. Обмеження MVP

У поточній версії проєкту:

- **не здійснюється запис даних до МІС**;
- **не використовується продуктивне API МІС**;
- **не реалізується синхронізація медичної документації з МІС**;
- усі інтеграційні сценарії працюють виключно через Mock Integration Layer;
- перехід до продуктивної інтеграції є окремим етапом розвитку системи та не входить до складу MVP.

# 86. Continuous Integration

5. Запуск Integration Tests.
6. Запуск Function (End-to-End) Tests.

8. Публікацію артефактів збірки.

У разі помилки будь-якого етапу зміни не можуть бути інтегровані до основної гілки.

## 90.3 Критерії якості

- критична бізнес-логіка покрита Unit Tests не менше ніж на **80%**;
- усі інтеграційні сценарії покриті Integration Tests;
- основні бізнес-процеси покриті Playwright Function Tests;
- відсутні критичні (Critical) та високопріоритетні (High) дефекти;
- усі зміни проходять повний CI Pipeline.

## 90.4 Критерії інтеграції

- Mock Adapter реалізує необхідні контракти API МІС;
- бізнес-логіка не містить прямих викликів API МІС;
- заміна Mock Adapter на Production Adapter не потребує змін Domain Layer або REST API.

3. GitHub Actions успішно завершує повний CI Pipeline.
4. Продемонстровано повний сценарій роботи системи на Mock-даних: від відкриття епізоду до формування та підписання PDF.
5. Замовнику передано вихідний код, документацію, інструкцію з розгортання та результати автоматизованого тестування.
