## 1. Паспорт процесу (Process Passport)

Заповнюється один раз на процес. Поля лягають у `prosthetics_flow_templates` (`FlowTemplate`).

| Поле | Значення для цього процесу | Куди лягає в коді | Коментар |
|---|---|---|---|

**Правила версіонування (з універсального шаблону):**
- Один `TP-LL-02` може мати багато версій; активною для `POST /instances` може бути лише одна (`status = ACTIVE`).
- `ARCHIVED` не використовується для нових інстансів; старі інстанси живуть зі своїм `templateSnapshot` (deep clone при `create()`, `TemplateSnapshotParser.toJson()`).

## 2. Контекст, передумови та межі

### 2.1 Бізнес-контекст

Процес забезпечує повний цикл виготовлення **протезів нижніх кінцівок** (гомілка, стегно; транстибіальні/трансфеморальні) у межах цеху протезно-ортопедичного підприємства. На відміну від верхніх кінцівок (тяговий протез передпліччя `TP-UL-01` — 10 етапів, акцент на тягах, кисті/гаку, ЗІЗ для термоформування), нижньокінцевий процес має **умовний пом'якшуючий вкладиш** (етап 8 — «не потрібен» як альтернатива) та **подвійний контроль якості поверхонь** (візуальний + тактильний для кожної гільзи окремо). Процес лінійний: після вилучення Quality Gate повернення та брак обробляються через стандартні механізми `backward` / `fail` без окремих контрольних точок.

`v1` фіксує 11 етапів від «Прийом замовлення» до «Видача протеза»; `v2` зберігає цю структуру, але формалізує її як виконуваний граф `FlowTemplate` з guard-ами, валідацією та машинами станів, сумісний з існуючим рушієм `prosthesis-manufacturing`.

### 2.2 Передумови (preconditions)

- Пацієнт існує в МІС (Doctor Eleks) і має активне замовлення типу `LOWER_LIMB`. Мінімально в замовленні: `patientId`, `orderNumber`, `productType = LOWER_LIMB`, `amputationLevel`, `limbSide`, `doctorName`, `prescriptionDate`, `materials` (може бути порожнім — доповнюється на етапі 6).
- Користувач автентифікований і має роль із секції 3 (перевіряється `@PreAuthorize` + `requireOwner`).
- Шаблон `TP-LL-02` у статусі `ACTIVE` (інакше `FlowInstanceService.create()` → 400 `Only active templates can be used for new instances`).
- Для етапів із пацієнтом (1, 5, 7, 10, 11) — пацієнт доступний (інакше — пауза `PATIENT`).

### 2.3 Що входить / не входить (scope)

| Входить | Не входить |
|---|---|
| Прийом замовлення та огляд (setup-фаза), зняття об'ємних розмірів, виготовлення та перевірка гіпсонегативу/позитиву, виготовлення та контроль тренувальної гільзи, примірки тренувальної гільзи/протеза, складання тренувального та постійного протезів, виготовлення пом'якшуючого вкладиша та постійної гільзи (з альтернативою), маркування, видача | Реабілітація та навчання ходьбі після видачі, біонічні/мiоелектричні вузли, логістика матеріалів поза цехом, білінг/фінанси, інтеграція з eHealth/ЛІС/PACS. Контроль якості як окремі Quality Gate — вилучено; перевірки поверхонь і посадки — як звичайні `CHECKBOX` кроків. |

### 2.4 Зовнішні системи та інтеграції

| Система | Напрям | Дані | Примітка |
|---|---|---|---|
| МІС (Doctor Eleks) через `MisApiClient` / `WireMockMisServiceImpl` | READ-only | `spzIBPatientSearch`, `spzIBPatientScheduleList`, `spzIBUserDetails`, `spzIBCompanyDetails`, `spzIB*Dictionary`, `sendPdf()` | Мутації МІС (`*Save`/`*Create`) — **заборонені** (`AGENTS.md` MIS Data Policy). Пацієнти/замовлення — дзеркала `prosthetics_patients` / `prosthetics_orders`. |
| Сховище файлів (Evidence) | WRITE | `EvidenceFile` (до 10 MB, `EvidenceFileService`) | Фото гіпсу/гільз, скани бланків замірів; `mimeTypes`/`maxSizeMb` задаються на `TemplateElement`. |
| PDF-генератор | WRITE | `ProstheticsPdfService.generateFinalReport` / `generateFailureReport` (iText) | Викликається з `FlowInstanceService.generateReport()`; при `FAILED` — failure-PDF. |

## 3. Ролі, відповідальності та RBAC

### 3.1 Ролі

| Роль (`UserRole`) | Призначення в цьому процесі | Типові дії |
|---|---|---|
| `PROSTHETIST` | Виконавець — проходить Wizard крок за кроком | `create instance`, `start`, `completeStep`, `pause/resume`, `backward`, `saveDraft`, `upload evidence`, `fail` (брак) |
| `PROSTHETICS_ADMINISTRATOR` | Адміністратор шаблонів | `create/update/archive template`, `view all instances` (`allowAll=true`) |
| `ADMINISTRATOR` | Системний адміністратор | `AUDIT_ACCESS`, `MODULE_ADMIN_ACCESS` (аудит-журнал, RBAC-матриця) |

### 3.2 Матриця дозволів (RBAC)

Керується `PermissionService` / `PermissionCatalog` (25 кодів), перевіряється в UI (`hasPermission`) та на бекенді (`@PreAuthorize("@permissionService.has('…')")`).

| Операція | Код дозволу | Ролі за замовчуванням | Примітка |
|---|---|---|---|
| Створити інстанс (`POST /instances`) | `PROSTHETICS_DASHBOARD` або `MODULE_PROSTHETICS_ACCESS` | `PROSTHETIST` | Перевіряє `template.status == ACTIVE` + відсутність активного інстансу на той самий `orderId` |
| Виконати крок (`POST /step-executions/{id}/complete`) | `PROSTHETICS_DASHBOARD` | `PROSTHETIST` (тільки `assignedUserId` — `requireOwner`) | Адмін бачить, але не виконує |
| Керувати шаблонами (`POST/PATCH /templates`) | `PROSTHETICS_TEMPLATES_MANAGE` | `PROSTHETICS_ADMINISTRATOR` |  |
| Переглядати чужі інстанси (`GET /instances/{id}`) | `allowAll=true` на `GET` | `PROSTHETICS_ADMINISTRATOR` | `requireOwner(id, userId, true)` |
| Завантажити доказ (`POST /evidence-files`) | `PROSTHETICS_DASHBOARD` | `PROSTHETIST` | Ліміт 10 MB |

### 3.3 Власність інстансу (ownership)

- `FlowInstance.assignedUserId` фіксується при `create()` = поточний користувач (`prosthetist1` / `prosthetist2` у сиді).
- `requireOwner(instanceId, userId, allowAll)` — єдиний гейт доступу: якщо `allowAll == false` і `assignedUserId != userId` → `404` (не `403`, щоб не розкривати існування).
- Пауза / відновлення / крок назад / fail / replacement — тільки власник.

### 4.3 Залежності між даними

```text
Пацієнт (МІС) ──1:N──► Замовлення (МІС) ──1:N──► Інстанс (локально, assignedUserId)
                                              │
                        Шаблон TP-LL-02 ──deep clone──► templateSnapshot (JSONB, незмінний, TemplateSnapshotParser.toJson())
                                              │
                                              ├─► StepExecution (1 на кожне проходження кроку, attemptNumber++ при backward)
                                              ├─► ResourceUsage (N на крок, матеріал обов'язковий)
                                              ├─► EvidenceFile (N на інстанс, прив'язка до StepExecution)
                                              └─► FailureSnapshot (0..1, при FAILED)
```

**Ключовий принцип (з універсального шаблону):** після `FlowInstanceService.create()` зв'язок із живою версією шаблону розривається — інстанс несе `templateSnapshot`. Зміни `TP-LL-02` не впливають на вже створені інстанси. Це дозволяє версіонувати нижньокінцевий процес без міграції історії.

## 5. Ієрархія шаблону: Stage → Step → Element

```
FlowTemplate TP-LL-02 (1)
  └─ TemplateStage (11 за v1; 10 у виконуваному інстансі — див. 5.2)
       └─ TemplateStep (1–2 на етап, разом 16 у інстансі)
            └─ TemplateElement (1–4 на крок, разом ~28 + STEP_MESSAGE)
```

Фізичні таблиці: `prosthetics_flow_templates`, `prosthetics_template_stages`, `prosthetics_template_steps`, `prosthetics_template_elements`.

### 5.1 Атрибути FlowTemplate

| Поле | Тип | Обмеження | Значення для TP-LL-02 |
|---|---|---|---|
| `name` | `varchar` | `NOT NULL`, унікальне з `template_version` | `TP-LL-02` |
| `description` | `text` | nullable | «Етапи технологічного процесу нижніх кінцівок — повний маршрут від гіпсонегативу до видачі (11 етапів v1, адаптовано під універсальний шаблон)» |
| `templateVersion` | `int` | `>=1` | `1` |
| `productType` | `ProductType` | `NOT NULL` | `LOWER_LIMB` |
| `amputationLevel` | `varchar(64)` | nullable | `generic_lower_limb` |
| `limbSide` | `LimbSide` | nullable | `BOTH` |
| `status` | `TemplateStatus` | `NOT NULL`, default `DRAFT` | `DRAFT` → `ACTIVE` |
| `estimatedDurationMin` | `int` | `>=0` | `540` |
| `stages` | `List<TemplateStage>` | `order_index` 0..N | 10 етапів у інстансі (див. 5.2) |

### 5.2 Етапи (TemplateStage)

> **Важливе рішення адаптації:** етап 1 v1 («Прийом замовлення та огляд пацієнта») — це **setup-фаза** (Screens 3–6 універсального шаблону: вибір пацієнта → замовлення → перегляд → вибір шаблону → `POST /instances`). Він **не** входить у граф виконуваного інстансу як `TemplateStage`, щоб не дублювати `ProstheticsContext` (`ProstheticsDraft: {patientId, orderId, templateId, instanceId}`). Для аудиторської повноти етап 1 документують як «Етап 0 — Setup» поза інстансом (див. рядок 0). Якщо потрібен слід у `StepExecution` — додають `ADMINISTRATIVE` етап 1 з одним `INFORMATION` кроком (опційно).

| # (v1) | # (v2, `orderIndex`) | Назва (v2) | `type` | `canSkip` | `requiresApproval` | Кроків | Пояснення |

### 5.5 Евристика розбиття (застосована до v1)

1. Кожен **розділ v1** (`## 1.` … `## 11.`) → один `TemplateStage` (крім розд. 1 → setup-фаза).
2. Кожен **підрозділ** (`### 2.1.` …) або група чекбоксів одного екрана → один `TemplateStep`.
3. Кожен **чекбокс / поле** → один `TemplateElement`.
4. Повідомлення `* В рамках цього кроку пацієнту надається послуга B-TR …` (якщо додається) → `STEP_MESSAGE`, `order_index=0`, `required=false`.
5. Група ЗІЗ (якщо з'явиться) → окремі `CHECKBOX` з префіксом `Засоби індивідуального захисту:`.
6. Крок із вимірами (1.1) → `MEASUREMENT`, guard «≥3 заповнених не-чекбоксів + усі required чекбокси» (8.1).

## 6. Машини станів

### 6.1 Життєвий цикл шаблону

```text
DRAFT ──publish──► ACTIVE ──archive──► ARCHIVED
  │                  │
  └────archive───────┘
```

- `create()` завжди `DRAFT`.
- `ACTIVE` — єдина версія, яку приймає `FlowInstanceService.create()`.
- `ARCHIVED` — термінальний; нові інстанси не створюються; старі живуть зі своїм `templateSnapshot`.

### 6.2 Життєвий цикл інстансу (`FlowInstanceStatus`)

```text
                    ┌── pause ──► PAUSED ── resume ──┐
                    │              │  ▲                │
NEW ── start ──► IN_PROGRESS ◄─────┘  └────────────────┘
                    │
                    ├─ backward ─► IN_PROGRESS (попередній крок, новий StepExecution, CANCELLED на поточному)
                    ├─ fail ──► FAILED (+ FailureSnapshot)
                    └─ completeStep (останній крок останнього етапу 10) ─► COMPLETED

FAILED ── replacement ─► NEW (новий інстанс, той самий orderId + snapshot)
```

| Статус | Термінальний? | Дозволені операції в цьому процесі |
|---|---|---|
| `NEW` | ні | `start`, `get`, `list` |
| `IN_PROGRESS` | ні | `completeStep`, `saveDraft`, `pause`, `backward`, `fail`, `upload evidence` |
| `PAUSED` | ні | `resume`, `get`, `list` |
| `COMPLETED` | так | `get`, `list`, `generateReport` (успіх) |
| `FAILED` | так | `get`, `list`, `generateFailureReport`, `replacement` |

Статуси `BLOCKED_PATIENT` / `BLOCKED_MATERIAL` — зарезервовані (зараз пауза з `PauseCategory`).

### 6.3 Життєвий цикл кроку (`StepExecutionStatus`)

```text
IN_PROGRESS ── completeStep ─► COMPLETED
     │
     ├── saveDraft ─► IN_PROGRESS (values оновлено, статус незмінний)
     ├── backward (з наступного кроку) ─► CANCELLED
     └── fail інстансу ─► (залишається IN_PROGRESS, інстанс FAILED)
```

- `attemptNumber` інкрементується при кожному `createExecution` на той самий `stepId` (backward).
- `priorStepValues` у `FlowInstanceResponse` — мапа `stepId → values` усіх `COMPLETED` (для read-only підсумків у Wizard).

## 7. Правила переходів і guard-и

| Перехід | Guard (умова) | Помилка (HTTP 400) | Застосування в цьому процесі |
|---|---|---|---|
| `create` | `template.status == ACTIVE` + немає активного інстансу на той самий `orderId` (`status ∉ {COMPLETED, FAILED}`) | `Only active templates…` / `An active instance already exists…` | `POST /instances` з `orderId` нижньої кінцівки + `TP-LL-02` |
| `start` | `instance.status == NEW` (ідемпотентно: `IN_PROGRESS` → повернути без змін) | `Instance can be started only from NEW status` | `POST /instances/{id}/start` |
| `completeStep` | `instance.status == IN_PROGRESS` + `execution.status == IN_PROGRESS` + `execution.stepId == currentStepId` + `validateValues()` (8.1) | `Step can be completed only while…` / `Only the current step…` / текст валідатора | Кожен крок 1.1–10.1: усі `CHECKBOX required=true` + для 1.1 `filled >=3` |
| `saveDraft` | ті самі, що `completeStep`, але без `validateValues()` | `Чернетку можна зберегти лише…` | Автозбереження бланку замірів (1.1) |
| `pause` | `status == IN_PROGRESS` | `Only an in-progress instance can be paused` | Очікування пацієнта (5/6/9) або матеріалу (3/8) |
| `resume` | `status == PAUSED` | `Only a paused instance can be resumed` |  |
| `backward` | `status == IN_PROGRESS` + не перший крок + `targetStep.allowBackward == true` | `Повернення неможливе: це перший крок…` / `…заборонено правилами шаблону` | Повернення на доопрацювання (замість колишніх Quality Gate) |
| `fail` | `status == IN_PROGRESS` | `Instance cannot be failed from its current status` | Ручний брак — кнопка «Брак» викликає `fail` або `backward` |
| `replacement` | `status == FAILED` | `Replacement is allowed only for failed instances` | Створює `NEW` з тим самим `orderId` + `snapshot` |
| `advance` (внутрішній) | — | — | Перехід між кроками/етапами |

**Hard Block у Wizard:** кнопка «Далі» / «Готово» заблокована, доки всі `required` елементи не `true` / не заповнені. Дублює серверний guard, але не замінює його.

**Специфіка цього процесу:**
- Крок 7.1 «Пом'якшуючий вкладиш» — `mandatory=false`; CTA «Пом'якшуючий вкладиш не потрібен» → `completeStep` з порожніми `values` (дозволено).
- Брак на етапах 7 і 10 v1 (неправильна посадка / дефект) — тепер через `fail(category, description)` або `backward` на кроки етапів 1–3, без окремих Quality Gate.

## 8. Валідація, бізнес-правила та обчислення

### 8.1 Валідація значень кроку (`FlowInstanceService.validateValues()`)

| Тип кроку | Правило | Повідомлення | Застосування |
|---|---|---|---|
| `MEASUREMENT` (крок 1.1) | `filledNonCheckboxValues >= 3` + кожен `CHECKBOX.required == true` → `value === true` | `Заповніть щонайменше 3 значення…` / `Поле «…» обов'язкове` | Бланк замірів: ≥3 числових розмірів |

| Крок 7.1 (умовний) | `mandatory=false` — валідація пропускається при порожніх `values` (варіант «не потрібен») | — | Альтернатива вкладиша |

### 8.2 Валідація шаблону (entity `@PrePersist/@PreUpdate`)

| Сутність | Правило | Перевірка для TP-LL-02 |
|---|---|---|
| `FlowTemplate` | `templateVersion >= 1`, `estimatedDurationMin >= 0` | `1`, `540` — OK |
| `TemplateStage` | `orderIndex >= 0` | `0–9` — OK |
| `TemplateStep` | `orderIndex >= 0`, `normDurationMin >= 0` | всі `>=0` — OK |
| `TemplateElement` | `orderIndex >= 0`, `minValue <= maxValue`, `minCount <= maxCount`, `maxSizeMb >= 1` | `CHECKBOX` без min/max — OK; `NUMERIC_INPUT` `0–200` — OK |
| `FlowInstance` | `totalActiveSeconds >= 0`, `totalIdleSeconds >= 0`, `reworkCount >= 0` | ініціалізація `0` — OK |

### 8.3 Обчислення часу

- `activeSeconds` кроку = `Duration.between(max(startedAt, resumedAt), completedAt)`.
- `totalActiveSeconds` — сума `activeDelta` при кожному `completeStep`.
- `totalIdleSeconds` — сума `Duration.between(pausedAt, resumedAt)` при `resume()`.
- Відображення — `HH:MM:SS` (`validation.ts: fmt()`), прогрес — `Math.round(done/total*100)` (`computeProgress()`).

## 11. Сценарії (flows)

### 11.1 Happy path — створення та повне проходження (без браку, вкладиш потрібен)

```text
Login (Screen 1) → Dashboard (Screen 2)
  → Вибір пацієнта (Screen 3, q=ПІБ) → Вибір замовлення LOWER_LIMB (Screen 4)
  → Перегляд замовлення + PDF прев'ю (Screen 5) → Вибір шаблону TP-LL-02 (Screen 6, фільтр LOWER_LIMB/generic_lower_limb/BOTH)
  → POST /instances {orderId, templateId} → NEW (deep clone snapshot)
  → Огляд карти (Screen 7, дерево 10 етапів) → POST /instances/{id}/start → IN_PROGRESS (крок 1.1, StepExecution attempt 1)
  → Wizard Screen 8: completeStep 1.1 (бланк ≥3) → 1.2 (чекбокс) → 2.1 → 2.2 → 3.1 → 3.2 → 4.1
  → 5.1 (комплектація+складання) → 6.1 (примірка трен.) 
  → 7.1 (вкладиш) → 7.2 (пост. гільза) → 8.1 (складання пост.) → 9.1 (примірка пост.) 
  → 10.1 (видача, 3 чекбокси) → COMPLETED → DoneScreen (Screen 15) → Експорт PDF (generateFinalReport) → Dashboard (архів)
```

### 11.2 Варіант «Пом'якшуючий вкладиш не потрібен»

На кроці 7.1 Wizard показує CTA «Пом'якшуючий вкладиш не потрібен». При натисканні — `completeStep` з `values="{}"` (дозволено, бо `mandatory=false` на кроці та `required=false` на його чекбоксах). `advance()` → крок 7.2. У PDF — позначка «Вкладиш не виготовлявся (за показаннями)».

### 11.3 Пауза / відновлення

`IN_PROGRESS --pause(PATIENT|MATERIAL|TECH_IDLE)--> PAUSED --resume--> IN_PROGRESS`. Типові точки: `MATERIAL` на 3.1 (немає пластику), `PATIENT` на 4.1/6.1/9.1 (пацієнт не з'явився), `TECH_IDLE` на 1.2/2.1 (сушіння гіпсу). Лічильники — 8.3.

### 11.4 Чернетка

`saveDraft(executionId, values, resources)` — часткове збереження бланку замірів (1.1) або комплектації (5.1) без валідації `required`; статус лишається `IN_PROGRESS`. Використовується для автозбереження у Wizard.

### 11.5 Крок назад (backward)

Дозволено лише якщо `targetStep.allowBackward == true` (у цьому процесі — `true` для всіх, крім 10.1 `false`). Поточне `IN_PROGRESS` → `CANCELLED`, нове `IN_PROGRESS` на цілі. Якщо крок — перший в етапі (напр. 3.1), ціль — останній крок попереднього етапу (2.2). Використовується для доопрацювання після виявлення дефекту посадки (замість колишніх Quality Gate).

### 11.6 Провал і заміна

`fail(category, description)` з `IN_PROGRESS` → `FAILED` + `FailureSnapshot`. Приклад: брак посадки на 6.1 або 9.1 → `fail(category=material_defect, description="Неправильне розташування м'яких тканин")`. `replacement(failedId)` → новий `NEW` з тим самим `orderId` + `snapshot` (дозволено лише для `FAILED`).

### 11.7 Розгалуження за типом кроку в цьому процесі

| `stepType` | Крок(и) | UI-віджет | Guard |
|---|---|---|---|
| `MEASUREMENT` | 1.1 | Форма бланку замірів (числові поля) | `≥3` не-чекбоксів + усі `required` чекбокси |
| `CHECKLIST` | 2.2, 3.2, 4.1, 5.1, 6.1, 7.1, 7.2, 9.1, 10.1 | `CheckboxRow` на весь рядок (клік будь-де) | усі `required` чекбокси `true` |
| `INFORMATION` | 1.2, 2.1, 3.1, 8.1 | `STEP_MESSAGE` (опційно) + чекбокс | чекбокс `true` |

- Кожна мутація (`CREATE`, `START`, `COMPLETE`, `DRAFT_SAVE`, `PAUSE`, `RESUME`, `BACKWARD`, `FAIL`, `REPLACEMENT`, `ARCHIVE`) → `auditService.logAction(entity, entityId, action, userId)` → `audit_logs` (immutable, `isDeleted=false`).

- Для нижньокінцевого процесу важливі записи `BACKWARD` (повернення на доопрацювання) та `FAIL` (причина браку).
