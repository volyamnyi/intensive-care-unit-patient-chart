# Універсальний шаблон опису технологічного процесу

> **Модуль:** `prosthesis-manufacturing` («Виробництво протезів»)
> **Призначення документа:** канонічний, повторно використовуваний шаблон для повного опису **будь-якого** технологічного процесу виготовлення протезно-ортопедичного виробу. Шаблон фіксує всі рівні деталізації — від паспорта процесу до окремих `TemplateElement` — та всі сценарії й логічні переходи між ними.
> **Еталонна інстанціація:** «Виготовлення протеза передпліччя з тяговим керуванням» (`TP-UL-01`, 10 етапів / 22 кроки, `data-prosth.sql`).
> **Аудиторія:** ШІ-агент, який проєктує / документує / імплементує новий процес; аналітик; розробник `prosthesis-manufacturing`.
> **Статус:** нормативний. Будь-який новий процес, описаний за цим шаблоном, має бути імплементований без відхилень від секцій 5–11, інакше — ArchUnit / контракт-тести впадуть.
> **Джерела істини:** `docs/Process Control System for the Manufacture of Prosthetics.md` (фази Screen 1–15), `docs/Операційна_карта_виготовлення_протеза_передпліччя_з_тяговим_керуванням/*.png` (18 аркушів операційної карти), код `prosthesis-manufacturing` (`FlowTemplate` → `FlowInstance` → `StepExecution`), `docs/General process description.md` (цей файл).

## Як користуватись шаблоном (інструкція для ШІ-агента)

1. **Скопіюй структуру** цього документа цілком. Не видаляй секції — якщо секція не застосовна, залиш заголовок і напиши `N/A — обґрунтування`.
2. **Заповни всі `{{PLACEHOLDER}}`** у секціях 1–4 конкретними значеннями нового процесу. Плейсхолдери позначені `{{LIKE_THIS}}`.
3. **Декомпозуй операційну карту** в ієрархію `Stage → Step → Element` за правилами секції 5. Кожен рядок операційної карти = один `TemplateStep` або один `TemplateElement` (див. 5.5 — евристика розбиття).
4. **Проітеруй валідатори** з секції 8: для кожного `Element` признач мінімальний достатній набір обмежень (`required`, `minValue`/`maxValue`, `regexPattern`, `options` тощо). Не додавай обмежень «про запас».
5. **Опиши переходи** в секції 7 у вигляді таблиці guard-ів.
6. **Пройди чекліст** секції 16. Документ вважається готовим, коли всі чекбокси `☐` відмічені.
7. **Згенеруй артефакти** з Додатку A (JSON/YAML скелет) — це вхід для `FlowTemplateService.create()` і для сиду `data-prosth.sql`.
8. **Не змінюй кодову базу** на етапі опису. Якщо бачиш розбіжність між шаблоном і кодом — зафіксуй її в секції 15 як `Known Gap`.

## 1. Паспорт процесу (Process Passport)

Заповнюється один раз на процес. Це «титульний аркуш» — його поля потрапляють у `prosthetics_flow_templates`.

| Поле | Тип / Обмеження | Заповнення для нового процесу | Куди лягає в коді |
|---|---|---|---|
| **Код / Назва шаблону** `{{TEMPLATE_CODE}}` | `name` — унікальне разом із `template_version` (`uq_flow_template_name_version`), 1–128 симв. | `{{TEMPLATE_CODE}}`, напр. `TP-UL-01` | `FlowTemplate.name` |
| **Версія** `{{VERSION}}` | `template_version >= 1`, автоінкремент на `name` | `{{VERSION}}` | `FlowTemplate.templateVersion` |
| **Опис** `{{DESCRIPTION}}` | вільний текст, 1–500 симв. | `{{DESCRIPTION}}` | `FlowTemplate.description` |
| **Тип виробу** `{{PRODUCT_TYPE}}` | `ProductType`: `UPPER_LIMB` \| `LOWER_LIMB` \| `{{NEW_TYPE}}` (розширюється) | `{{PRODUCT_TYPE}}` | `FlowTemplate.productType` |
| **Рівень ампутації** `{{AMPUTATION_LEVEL}}` | рядок 0–64, бажано з контрольованого словника (напр. `upper_third_forearm`) | `{{AMPUTATION_LEVEL}}` | `FlowTemplate.amputationLevel` |
| **Сторона** `{{LIMB_SIDE}}` | `LimbSide`: `LEFT` \| `RIGHT` \| `BOTH` \| `null` | `{{LIMB_SIDE}}` | `FlowTemplate.limbSide` |
| **Статус** | `TemplateStatus`: `DRAFT` → `ACTIVE` → `ARCHIVED` | `DRAFT` на старті | `FlowTemplate.status` |
| **Оцінна тривалість** `{{EST_MIN}}` | `estimatedDurationMin >= 0`, хв (сума `normDurationMin` — довідково) | `{{EST_MIN}}` | `FlowTemplate.estimatedDurationMin` |
| **Кількість етапів / кроків** | похідне від секції 5 | `{{STAGES}}` / `{{STEPS}}` | `stages.size()` / `steps.size()` |
| **Власник / Автор** | `createdBy` (userId) | `{{OWNER}}` | `BaseEntity.createdBy` |
| **Дата введення** | ISO-8601 | `{{DATE}}` | `BaseEntity.createdAt` |
| **Операційна карта (джерело)** | посилання на PDF/PNG (18 аркушів для еталона) | `{{SOURCE_DOC}}` | поза БД, у цьому документі |

**Правила:**
- Один `{{TEMPLATE_CODE}}` може мати багато версій; активною для створення інстансів може бути лише одна версія (`status = ACTIVE` — перевіряє `FlowInstanceService.create()`).
- `ARCHIVED` — термінальний, не використовується для нових інстансів, але старі інстанси продовжують жити зі своїм `templateSnapshot`.

## 3. Ролі, відповідальності та RBAC

### 3.1 Ролі

| Роль (`UserRole`) | Призначення в процесі | Типові дії |
|---|---|---|
| `PROSTHETIST` | Виконавець — проходить Wizard крок за кроком | `create instance`, `start`, `completeStep`, `pause/resume`, `backward`, `upload evidence` |
| `PROSTHETICS_ADMINISTRATOR` | Адміністратор шаблонів | `create/update/archive template`, `view all instances` |
| `ADMINISTRATOR` | Системний адміністратор | `AUDIT_ACCESS`, `MODULE_ADMIN_ACCESS` |
| `{{CUSTOM_ROLE}}` | `{{RESPONSIBILITY}}` | `{{ACTIONS}}` |

### 3.2 Матриця дозволів (RBAC)

Матриця керується через `PermissionService` / `PermissionCatalog` (25 кодів) і перевіряється в UI (`hasPermission`) та на бекенді (`@PreAuthorize("@permissionService.has('…')")`).

| Операція | Код дозволу | Ролі за замовчуванням | Примітка |
|---|---|---|---|
| Створити інстанс (`POST /instances`) | `PROSTHETICS_DASHBOARD` або `MODULE_PROSTHETICS_ACCESS` | `PROSTHETIST` | |
| Виконати крок (`POST /step-executions/{id}/complete`) | `PROSTHETICS_DASHBOARD` | `PROSTHETIST` (тільки `assignedUserId` — `requireOwner`) | Адмін бачить, але не виконує |
| Керувати шаблонами (`POST/PATCH /templates`) | `PROSTHETICS_TEMPLATES_MANAGE` | `PROSTHETICS_ADMINISTRATOR` | |
| Переглядати чужі інстанси | `allowAll=true` на `GET` | `PROSTHETICS_ADMINISTRATOR` | `requireOwner(..., allowAll)` |

> Для нового процесу додай рядок на кожну специфічну операцію (напр. «підпис B-TR послуги»).

### 3.3 Власність інстансу (ownership)

- `FlowInstance.assignedUserId` фіксується при `create()` = поточний користувач.
- `requireOwner(instanceId, userId, allowAll)` — єдиний гейт доступу: якщо `allowAll == false` і `assignedUserId != userId` → `404` (не `403`, щоб не розкривати існування).
- Пауза / відновлення / крок назад / fail / replacement — тільки власник.

### 4.3 Залежності між даними

```text
Пацієнт (МІС) ──1:N──► Замовлення (МІС) ──1:N──► Інстанс (локально)
                                              │
                        Шаблон ──deep clone──► templateSnapshot (JSONB, незмінний)
                                              │
                                              ├─► StepExecution (1 на кожне проходження кроку, attemptNumber++)
                                              ├─► ResourceUsage (N на крок)
                                              ├─► EvidenceFile (N на інстанс)
                                              └─► FailureSnapshot (0..1, при FAILED)
```

**Ключовий принцип:** після `FlowInstanceService.create()` зв'язок із живою версією шаблону розривається — інстанс несе `templateSnapshot` (повний граф, серіалізований `TemplateSnapshotParser.toJson()`). Зміни шаблону не впливають на вже створені інстанси.

## 5. Ієрархія шаблону: Stage → Step → Element

```
FlowTemplate (1)
  └─ TemplateStage (N, order_index)
       └─ TemplateStep (N, order_index)
            └─ TemplateElement (N, order_index)
```

Фізичні таблиці: `prosthetics_flow_templates`, `prosthetics_template_stages`, `prosthetics_template_steps`, `prosthetics_template_elements`.

### 5.1 Атрибути FlowTemplate

| Поле | Тип | Обмеження | Опис |
|---|---|---|---|
| `name` | `varchar` | `NOT NULL`, унікальне з `template_version` | Людська назва (напр. «Операційна карта виготовлення протеза передпліччя з тяговим керуванням») |
| `description` | `text` | nullable | Розгорнутий опис, посилання на операційну карту |
| `templateVersion` | `int` | `>=1` | Версія; автоінкремент по `name` у `FlowTemplateService.create()` |
| `productType` | `ProductType` enum | `NOT NULL` | `UPPER_LIMB` / `LOWER_LIMB` / `{{NEW}}` |
| `amputationLevel` | `varchar(64)` | nullable | Словникове значення (напр. `upper_third_forearm`) |
| `limbSide` | `LimbSide` enum | nullable | `LEFT` / `RIGHT` / `BOTH` |
| `status` | `TemplateStatus` | `NOT NULL`, default `DRAFT` | `DRAFT` → `ACTIVE` → `ARCHIVED` |
| `estimatedDurationMin` | `int` | `>=0` | Сумарна оцінка, довідково |
| `stages` | `List<TemplateStage>` | `order_index` 0..N | Впорядкований список етапів |

### 5.2 Атрибути TemplateStage (Етап)

| Поле | Тип | Обмеження | Опис |
|---|---|---|---|
| `name` | `varchar` | `NOT NULL` | Назва етапу (напр. «Зняття мірок та виготовлення гіпсового негатива») |
| `type` | `StageType` | `NOT NULL` | `CLINICAL` (з пацієнтом) / `TECHNICAL` (цех) / `ADMINISTRATIVE` (оформлення) |
| `orderIndex` | `int` | `>=0` | Порядок у шаблоні |
| `canSkip` | `boolean` | default `false` | Чи можна пропустити етап цілком (рідко `true`) |
| `requiresApproval` | `boolean` | default `false` | Чи потрібен підпис/затвердження етапу |
| `steps` | `List<TemplateStep>` | `>=1` | Кроки етапу |

> **Евристика виділення етапів:** один етап = одна логічно замкнута виробнича фаза з одним місцем виконання (кабінет / гіпсовка / цех / примірочна) і одним набором ЗІЗ. В еталоні — 10 етапів (див. секцію 17).

### 5.3 Атрибути TemplateStep (Крок)

| Поле | Тип | Обмеження | Опис |
|---|---|---|---|
| `name` | `varchar` | `NOT NULL` | Назва кроку (напр. «Зняття мірок (з пацієнтом)») |
| `description` | `text` | nullable | Детальна інструкція з операційної карти |
| `stepType` | `StepType` | `NOT NULL` | `INFORMATION` / `MEASUREMENT` / `CHECKLIST` / `MEDIA` / `SELECTION` / `COMPOSITE` |
| `mandatory` | `boolean` | default `true` | Чи обов'язковий крок для прогресу |
| `allowBackward` | `boolean` | default `true` | Чи дозволено повернутись на цей крок через «Назад» |
| `autoStartTimer` | `boolean` | default `false` | Чи стартує таймер активності автоматично при вході |
| `normDurationMin` | `int` | `>=0` | Норма часу (довідково, для план-факт) |
| `elements` | `List<TemplateElement>` | `>=0` | Поля / чекбокси / повідомлення кроку |

**Типи кроків — коли що використовувати:**

| `stepType` | Коли | Типовий вміст |
|---|---|---|
| `MEASUREMENT` | Знімаються числові / антропометричні параметри | `NUMERIC_INPUT` + `TEXT_INPUT` + обов'язковий `CHECKBOX` підтвердження; guard: `filled >= 3` (див. 8.1) |
| `CHECKLIST` | Потрібно підтвердити факт виконання кожної дії | `CHECKBOX` * N, усі `required=true` |
| `INFORMATION` | Інструктивний крок із підтвердженням | `STEP_MESSAGE` (B-TR послуга) + 1–2 `CHECKBOX` |
| `SELECTION` | Вибір комплектації | `TEXT_INPUT` (Кисть/Гак/Бандаж), `TEXTAREA`, `DROPDOWN`/`RADIO` |
| `MEDIA` | Потрібен фото-/відео-доказ | `IMAGE_UPLOAD` / `FILE_UPLOAD` + `CHECKBOX` |
| `COMPOSITE` | Змішаний крок (виміри + чекліст + ЗІЗ) | комбінація вище |

### 5.4 Атрибути TemplateElement (Елемент кроку)

| Поле | Тип | Обмеження | Опис |
|---|---|---|---|
| `elementType` | `ElementType` | `NOT NULL` | Див. каталог нижче |
| `label` | `varchar` | `NOT NULL` | Текст поля / чекбокса (напр. «Гіпсовий негатив виготовлено») |
| `placeholder` | `varchar` | nullable | Підказка в полі вводу |
| `required` | `boolean` | default `false` | Чи обов'язкове поле для `completeStep` |
| `unit` | `varchar(32)` | nullable | Одиниця виміру (см, кг, хв) |
| `minValue` / `maxValue` | `BigDecimal(12,3)` | `min <= max` | Діапазон для `NUMERIC_INPUT` |
| `minCount` / `maxCount` | `int` | `min <= max` | Довжина тексту або кількість значень |
| `regexPattern` | `varchar` | nullable | Регулярний вираз для `TEXT_*` |
| `options` | `jsonb` | nullable | Список опцій для `DROPDOWN`/`RADIO` |
| `mimeTypes` | `varchar` | nullable | Дозволені MIME для `FILE_UPLOAD`/`IMAGE_UPLOAD` |
| `maxSizeMb` | `int` | `>=1` | Ліміт файлу |
| `validationRules` | `jsonb` | nullable | Довільні додаткові правила (резерв) |
| `orderIndex` | `int` | `>=0` | Порядок у кроці |

**Каталог `ElementType`:**

| Тип | Призначення | Специфічні поля | Валідація |
|---|---|---|---|
| `CHECKBOX` | Підтвердження факту | `required` | `value === true` якщо `required` |
| `TEXT_INPUT` | Короткий текст | `placeholder`, `minCount/maxCount`, `regexPattern` | довжина + regex |
| `TEXTAREA` | Довгий текст | `placeholder`, `minCount/maxCount` | довжина |
| `NUMERIC_INPUT` | Число | `unit`, `minValue/maxValue` | `isNaN` + діапазон |
| `DROPDOWN` | Вибір одного зі списку | `options` (jsonb) | `value ∈ options` |
| `RADIO` | Радіо-група | `options` | `value ∈ options` |
| `DATE_PICKER` | Дата | — | ISO-8601 |
| `FILE_UPLOAD` | Файл | `mimeTypes`, `maxSizeMb` | MIME + розмір |
| `IMAGE_UPLOAD` | Зображення | `mimeTypes`, `maxSizeMb` | MIME + розмір |
| `SIGNATURE_CAPTURE` | Ел. підпис | — | наявність blob |
| `STEP_MESSAGE` | Read-only інфо-блок (B-TR послуга) | `label` — текст повідомлення | не валідується, `required` завжди `false` |

### 5.5 Евристика розбиття операційної карти

1. Кожен **розділ операційної карти** з окремим заголовком → один `TemplateStage`.
2. Кожен **нумерований пункт** усередині розділу → один `TemplateStep`.
3. Кожен **чекбокс / поле / повідомлення** пункту → один `TemplateElement`.
4. Повідомлення виду `* В рамках цього кроку пацієнту надається послуга B-TR …` → `STEP_MESSAGE` з `order_index = 0`, `required = false`.
5. Група ЗІЗ (окуляри, респіратор, навушники, рукавички) → окремі `CHECKBOX` з префіксом `Засоби індивідуального захисту:`.
6. Якщо крок містить і виміри, і чекбокси — тип кроку `MEASUREMENT`, валідація за правилом «≥3 заповнених не-чекбоксів + усі required чекбокси» (див. 8.1).

## 6. Машини станів

### 6.1 Життєвий цикл шаблону

```text
DRAFT ──publish──► ACTIVE ──archive──► ARCHIVED
  │                  │
  └────archive───────┘
```

- `create()` завжди `DRAFT`.
- `ACTIVE` — єдина версія, яку приймає `FlowInstanceService.create()`.
- `ARCHIVED` — термінальний; нові інстанси не створюються.

### 6.2 Життєвий цикл інстансу (`FlowInstanceStatus`)

```text
                    ┌── pause ──► PAUSED ── resume ──┐
                    │              │  ▲                │
NEW ── start ──► IN_PROGRESS ◄─────┘  └────────────────┘
                    │
                    ├─ backward ─► IN_PROGRESS (попередній крок, новий StepExecution)
                    ├─ fail ──► FAILED (+ FailureSnapshot)
                    └─ completeStep (останній крок останнього етапу) ─► COMPLETED

FAILED ── replacement ─► NEW (новий інстанс, той самий orderId + snapshot)
```

Статуси `BLOCKED_PATIENT` / `BLOCKED_MATERIAL` — зарезервовані для майбутніх блокувань (зараз пауза з `PauseCategory`).

| Статус | Термінальний? | Дозволені операції |
|---|---|---|
| `NEW` | ні | `start`, `get`, `list` |
| `IN_PROGRESS` | ні | `completeStep`, `pause`, `backward`, `fail`, `upload evidence` |
| `PAUSED` | ні | `resume`, `get`, `list` |
| `COMPLETED` | так | `get`, `list`, `generateReport` |
| `FAILED` | так | `get`, `list`, `generateFailureReport`, `replacement` |

### 6.3 Життєвий цикл кроку (`StepExecutionStatus`)

```text
IN_PROGRESS ── completeStep ─► COMPLETED
     │
     ├── backward (з наступного кроку) ─► CANCELLED (попереднє виконання скасоване)
     └── fail інстансу ─► (залишається IN_PROGRESS, інстанс FAILED)
```

- `attemptNumber` інкрементується при кожному `createExecution` на той самий `stepId` (backward).
- `priorStepValues` у `FlowInstanceResponse` — зведена мапа `stepId → values` усіх `COMPLETED` виконань (для read-only підсумків у Wizard).

## 7. Правила переходів і guard-и

| Перехід | Guard (умова) | Помилка (HTTP 400) |
|---|---|---|
| `create` | `template.status == ACTIVE` + немає активного інстансу на той самий `orderId` (`status ∉ {COMPLETED, FAILED}`) | `Only active templates…` / `An active instance already exists…` |
| `start` | `instance.status == NEW` (ідемпотентно: `IN_PROGRESS` → повернути без змін) | `Instance can be started only from NEW status` |
| `completeStep` | `instance.status == IN_PROGRESS` + `execution.status == IN_PROGRESS` + `execution.stepId == currentStepId` + `validateValues()` пройшла | `Step can be completed only while…` / `Only the current step…` / текст валідатора (8.1) |
| `pause` | `status == IN_PROGRESS` | `Only an in-progress instance can be paused` |
| `resume` | `status == PAUSED` | `Only a paused instance can be resumed` |
| `backward` | `status == IN_PROGRESS` + не перший крок процесу + `targetStep.allowBackward == true` | `Повернення неможливе: це перший крок…` / `…заборонено правилами шаблону` |
| `fail` | `status == IN_PROGRESS` | `Instance cannot be failed from its current status` |
| `replacement` | `status == FAILED` | `Replacement is allowed only for failed instances` |
| `advance` (внутрішній) | — | — |

**Hard Block у Wizard (UI):** кнопка «Готово / Завершити крок» заблокована, доки всі `required` елементи не заповнені / не підтверджені. Це дублює серверний guard, але не замінює його.

## 8. Валідація, бізнес-правила та обчислення

### 8.1 Валідація значень кроку (`FlowInstanceService.validateValues()`)

| Тип кроку | Правило | Повідомлення |
|---|---|---|
| `MEASUREMENT` | `filledNonCheckboxValues >= 3` + кожен `CHECKBOX.required == true` → `value === true` + хардкод `ppe-measurement-non-sterile-gloves === true` для `e0000002` | `Заповніть щонайменше 3 значення…` / `Поле «…» обов'язкове` |
| `INFORMATION` / `CHECKLIST` / `SELECTION` / `MEDIA` / `COMPOSITE` | кожен `required` → `!isBlank(value)`; `TEXT_*` → `regexPattern`; `NUMERIC_INPUT` → `isNaN` + `minValue/maxValue`; `DROPDOWN/RADIO` → `value ∈ options`; `minCount/maxCount` → `countValues` | `Поле «…» обов'язкове` / `…не відповідає формату` / `…має бути числом` / `…має бути не менше/більше…` / `…має недопустиме значення` |

### 8.2 Валідація шаблону (entity `@PrePersist/@PreUpdate`)

| Сутність | Правило |
|---|---|
| `FlowTemplate` | `templateVersion >= 1`, `estimatedDurationMin >= 0` |
| `TemplateStage` | `orderIndex >= 0` |
| `TemplateStep` | `orderIndex >= 0`, `normDurationMin >= 0` |
| `TemplateElement` | `orderIndex >= 0`, `minValue <= maxValue`, `minCount <= maxCount`, `maxSizeMb >= 1` |
| `FlowInstance` | `totalActiveSeconds >= 0`, `totalIdleSeconds >= 0`, `reworkCount >= 0` |

### 8.3 Обчислення часу

- `activeSeconds` кроку = `Duration.between(max(startedAt, resumedAt), completedAt)`.
- `totalActiveSeconds` інстансу — сума `activeDelta` при кожному `completeStep`.
- `totalIdleSeconds` — сума `Duration.between(pausedAt, resumedAt)` при кожному `resume()`.
- Формат відображення — `HH:MM:SS` (`validation.ts: fmt()`), прогрес — `Math.round(done/total*100)` (`computeProgress()`).

### 8.4 Процес-специфічні правила (заповни для нового процесу)

| # | Правило | Тип | Де перевіряється |
|---|---|---|---|
| R1 | `{{RULE_1}}` (напр. «довжина кукси 8–35 см») | `NUMERIC_INPUT` range | `TemplateElement.minValue/maxValue` + `validateValues()` |
| R2 | `{{RULE_2}}` (напр. «матеріали зі словника BOM») | `DROPDOWN` options | `options` jsonb |
| R3 | `{{RULE_3}}` (напр. «фото гіпсу обов'язкове») | `IMAGE_UPLOAD` required | `required=true` |
| `{{N}}` | `{{RULE_N}}` | `{{TYPE}}` | `{{WHERE}}` |

## 9. Час, паузи та блокування

| Поняття | Поле | Семантика |
|---|---|---|
| **Активний час** | `totalActiveSeconds`, `StepExecution.activeSeconds` | Час, коли інстанс у `IN_PROGRESS` і крок у `IN_PROGRESS` |
| **Пауза** | `status=PAUSED`, `pausedAt`, `pauseCategory`, `resumedAt` | Зупиняє накопичення активного часу; `resume()` додає `idleDelta` в `totalIdleSeconds` |
| **Категорія паузи** | `PauseCategory`: `PATIENT` (чекаємо пацієнта) / `MATERIAL` (немає матеріалів) / `TECH_IDLE` (технологічний простій — сушіння/полімеризація) | Обирається користувачем при `pause()` |
| **Норма часу кроку** | `TemplateStep.normDurationMin` | Довідково; факт vs норма — у PDF |
| **Оцінна тривалість** | `FlowTemplate.estimatedDurationMin` | Сума норм, довідково |

**Правила:**
- Пауза можлива лише з `IN_PROGRESS`.
- Під час `PAUSED` кроки не виконуються, `completeStep`/`backward` — 400.

## 10. Доказова база: файли, ресурси, підписи

| Сутність | Таблиця / Сервіс | Поля | Обмеження |
|---|---|---|---|
| **Доказовий файл** | `prosthetics_evidence_files` / `EvidenceFileService` | `fileName`, `mimeType`, `sizeBytes`, `checksum`, `instanceId`, `stepExecutionId` | `size <= 10 MB`, `mime ∈ {image/*, application/pdf}` (налаштовується через `TemplateElement.mimeTypes/maxSizeMb`) |

## 11. Сценарії (flows)

### 11.1 Happy path — створення та повне проходження

```text
Login (Screen 1) → Dashboard (Screen 2) → Вибір пацієнта (Screen 3)
  → Вибір замовлення (Screen 4) → Перегляд замовлення (Screen 5, PDF прев'ю)
  → Вибір шаблону (Screen 6, фільтр ProductType/AmputationLevel/LimbSide)
  → Створення інстансу (POST /instances, status NEW, deep clone snapshot)
  → Огляд технологічної карти (Screen 7, дерево Stage→Step)
  → Старт (POST /instances/{id}/start, status IN_PROGRESS, перший StepExecution)
  → [Wizard Screen 8] completeStep × N (з advance між кроками/етапами)
  → COMPLETED → DoneScreen (Screen 15) → Експорт PDF → Dashboard (архів)
```

### 11.2 Пауза / відновлення

`IN_PROGRESS --pause(PATIENT|MATERIAL|TECH_IDLE)--> PAUSED --resume--> IN_PROGRESS`. Лічильники часу — секція 8.3.

### 11.3 Крок назад (backward)

Дозволено лише якщо `allowBackward == true` на **цільовому** кроці. Поточне `IN_PROGRESS` виконання → `CANCELLED`, створюється нове `IN_PROGRESS` на цілі. Якщо крок — перший в етапі, ціль — останній крок попереднього етапу.

### 11.4 Провал і заміна

`fail(category, description)` з `IN_PROGRESS` → `FAILED` + `FailureSnapshot`. `replacement(failedInstanceId)` → новий `NEW` інстанс із тим самим `orderId` + `templateSnapshot` (дозволено лише для `FAILED`).

### 11.5 Розгалуження за типом кроку

| `stepType` | UI-віджет | Guard переходу |
|---|---|---|
| `MEASUREMENT` | Форми вимірів (антропометрія) | `≥3` не-чекбоксів заповнено + усі `required` чекбокси |
| `CHECKLIST` | Список чекбоксів на весь рядок (`CheckboxRow`) | усі `required` чекбокси `true` |
| `SELECTION` | Текстові поля комплектації | `CHECKBOX «Комплектацію сформовано» == true` |
| `INFORMATION` | `STEP_MESSAGE` + 1–2 чекбокси | чекбокси `true` |
| `MEDIA` | Завантаження файлу + чекбокс | файл завантажено + чекбокс |

### 17.4 Характерні патерни еталона
