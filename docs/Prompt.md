# MIGRATION STRATEGY

Поточний проєкт є результатом суттєвого перегляду архітектури.

Допускається повний рефакторинг будь-якого компонента системи.

Якщо існуюча реалізація суттєво відрізняється від нового Технічного завдання, агент повинен:

1. Видалити застарілу реалізацію.
2. Побудувати нову реалізацію відповідно до ТЗ.
3. Видалити всі застарілі тести.
4. Створити нові тести.
5. Оновити документацію.
6. Переконатися, що система повністю проходить CI.

Не допускається збереження застарілої архітектури лише заради сумісності зі старим кодом.

Нове Технічне завдання має абсолютний пріоритет над існуючою реалізацією.

# BEFORE ANY MODIFICATION

Перед будь-якою зміною необхідно:

1. Проаналізувати існуючий код.

2. Знайти місце у ТЗ.

3. Порівняти реалізацію з ТЗ.

4. Побудувати план міграції.

5. Лише після цього змінювати код.

---

Не змінюй API без причини.

Не створюй дублікати логіки.

Не створюй нові абстракції якщо вони не потрібні.

Не оптимізуй передчасно.

# TESTING

Стара тестова база більше не є джерелом істини.

Після аналізу нової архітектури необхідно повністю видалити всі існуючі автоматизовані тести, якщо вони не відповідають новому Технічному завданню.

Не допускається адаптація або часткове виправлення старих тестів.

Необхідно створити новий набір тестів відповідно до нової архітектури та нового бізнес-процесу.

Обов'язково видалити:

- усі Backend Unit Tests;
- усі Frontend Unit Tests;
- усі Integration Tests;
- усі Playwright Function (E2E) Tests;
- застарілі тестові fixtures;
- застарілі mock-и;
- застарілі test utilities;
- застарілі тестові дані.

Після завершення міграції необхідно створити новий набір тестів.

Обов'язкові категорії:

Backend

- JUnit 5 Unit Tests

Frontend

- Vitest Unit Tests

Integration

- Spring Integration Tests

Function

- Microsoft Playwright E2E Tests

Усі нові тести повинні бути написані виключно відповідно до нового Технічного завдання.

Не допускається повторне використання тестів, що перевіряють застарілу бізнес-логіку.
